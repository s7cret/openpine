# Этап 1 из 8 — архитектурные контракты и проверяемая приёмка

База: `b738fcce4e34d13b718720a900e5f9eab66a797a`. Исходные 36 задач не заменяются
новым сокращённым списком. `verification/stages.json` связывает каждый OP-01–OP-35
ровно с одним этапом; OP-36 сохраняется принятым в прежнем объёме. Связь с исходным
ТЗ проверяется по SHA256 из `docs/RC6_REVIEW_36.json`.

## Что означает завершение этого этапа

Принимается инфраструктура, на которой заканчиваются следующие подсистемы: один
контракт конфигурации на границе исполнения, проверяемые владельцы семантики,
карта установленных возможностей, фиксированный корпус и обязательный CI без
молчаливого сокращения тестов. Это **не полное закрытие широких OP-03/12/15/32/35**:
они остаются сквозными до финальной поставки. Версионная семантика и полный каталог
принимаются на этапе 2, брокер на 5, immutable wheel-only поставка на 8.

## Конфигурация без второй бизнес-логики

`openpine.runtime.rc6_config.resolve_engine_config` по-прежнему проверяет транспорт,
хеш, допущенный инструмент и правила существующего BacktestConfig. Новый снимок
содержит уже разрешённые значения и проверяемую цепочку происхождения. Он хранит
канонические bytes, не отдаёт изменяемые внутренние словари и позволяет обнаружить
изменение settings после допуска через `assert_matches()`.

В generated session сверка выполняется при создании, не на каждом баре. Движок
сохраняет свой рабочий mutable объект; принудительной заморозки его внутренних
переходов не добавлено. В bulk и interactive возвращается компактный
`effective_config_evidence`, без дублирования большого request dataset в отчёте.
Существующий effective_config_hash не заменён несовместимой формулой.

Граница существенна: старый вызов уже приносит частично объединённые настройки.
Его нельзя честно разложить обратно на пользовательские overrides, Pine declaration
и version defaults. Такие значения отмечаются `submitted`, а receipt содержит
`upstream_provenance=unresolved_before_admission`. Полное происхождение на входах
CLI/API и version-defaults остаётся критерием OP-03; архитектурный контракт теперь
явный, но его отсутствие у старого вызывающего кода не замаскировано.

## Владельцы семантики

Contracts владеет схемами и каноническими идентичностями; Pine2AST — синтаксисом,
версиями и типами; Ast2Python — IR/lowering; PineLib — значениями, сериями и
выражениями запросов; MarketData Provider — данными и календарями; Engine —
ордерами/исполнениями/ledger; Optimizer — поиском и контрактом trial; OpenPine —
оркестрацией, допуском, хранением и UX.

`architecture.py` проверяет допустимые направления зависимостей и известные точки
`resolve_engine_config`, `serialize_engine_config`, `process_bar_fills`,
`resolve_exit_prices`. Отчёт включает хеш исходников каждого компонента. Это
статический архитектурный барьер, не доказательство отсутствия любой возможной
семантической копии под другим именем. Произвольно вычисляемые import-строки и
изоляция процессов требуют отдельных runtime/fault-проверок; sandbox не заменён.

## Карта возможностей и exact target

`capabilities.py` не содержит вручную нарисованного процента совместимости. В
отчёте остаются BOUND, UNAVAILABLE и UNVERIFIED, отдельно — необходимость dataset
и отсутствие внешнего oracle. BOUND означает связанную цепочку, не численную
совместимость. Знаменатель — установленный каталог, не доказательство полноты
официального Pine на какую-либо дату.

В Ast2Python исправлен реальный fail-open: валидный по хешу exact manifest мог
не содержать operator.binary, operator.unary или series.history, и загрузчик
унаследовал бы reference-операцию. Теперь отсутствие любой из трёх runtime-точек
или дубликат отклоняются. Остальные reference-описания структурного lowering
остаются собственностью компилятора и не выдаются за runtime fallback.

Компиляция дополнительно проверяет фактические callable используемых операций.
`compile_meta.effective_target` связывает версию, каталог, target hash, host surface
и режим. Это идентичность для дальнейшего кеширования, **не закрытие OP-24**:
полный cache hit/miss/invalidation gate относится к этапу 6. Защита host/worker и
их прежняя проверка возможностей сохранены.

## Корпус и первый divergence

`verification/corpus-v1` хранит source, отдельные свечи/settings и вручную
выведенные expected traces. Варианты для v1–v6 покрывают реальный market entry на
следующей цене открытия и отсутствие сделки. Они исполняются через настоящий
компилятор и брокер в bulk/interactive; локальное сравнение транспорта использует
существующую in-memory обвязку. Два дополнительных теста запускают защищённые
worker-процессы и проверяют конфигурационный receipt.

Компаратор не исполняет Pine повторно и не генерирует expected из тестируемого
движка. Он проверяет source/data/config identities, типы значений, порядок
событий, явные допуски и первое различие с bar/phase/source_span, когда эти
координаты присутствуют. `false`, 0, `null`, маркер na и отсутствующее поле не
смешиваются. Пропуск, отсутствующий expected или исполнение, которое не завершилось,
остаются в знаменателе и не считаются успехом. Изменение корпуса требует явного
обновления `corpus-lock.json`.

Режим tradingview требует внешних ожидаемых данных; manual fixtures не получают
`tradingview_verified=true`. Сам текст provenance и checksum не удостоверяют
внешний источник против автора, который может изменить все файлы и все хеши.
Проверка происхождения TV-экспортов остаётся отдельной процедурой приёмки.

## Команды

```sh
python -m openpine.verification architecture --stack-root /path/to/stack --output architecture.json
python -m openpine.verification capabilities --mode interactive --output capabilities.json
python -m openpine.verification compare --corpus verification/corpus-v1/manifest.json \
  --observations observations.json --expected-hash sha256:CORPUS_HASH --output comparison.json
python -m openpine.verification stage1 --host-root . --stack-root /path/to/stack --evidence evidence
```

Последняя команда принимает только результаты реально выполненных обязательных
наборов, совпадающие с `verification/inventory.json`, и observations каждого
случая. `pytest --collect-only` создаёт лишь проект inventory и **не подтверждает
прохождение**. Разрешены только пять явно исключённых внешних сетевых тестов
провайдера; пропуски обязательных тестов не становятся зелёными.

Добавление/удаление/переименование теста требует проверяемого изменения inventory
в том же этапе. Не запускаем все библиотеки после каждой строки: разработка идёт
по целевым тестам, единый закреплённый gate — перед общей приёмкой и публикацией.
