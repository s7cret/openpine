# Получение истории и live R6

Переносимый экспорт и офлайн-проверка записанной сессии: [SESSIONS.md](SESSIONS.md).

Все семь частей находятся в этом монорепозитории. Python 3.14.8, SQLite
3.54.1, закреплённая DuckDB 2.0 prerelease, Parquet/ZSTD и `websockets==17.2`.
Исполнение Pine v1–v6 сохраняет прежние закреплённые правила языка. Это наша
модель исполнения; точное сравнение с TradingView остаётся отдельным этапом.

## 1. Идентичности и возможности

`InstrumentKey` содержит exchange/market/symbol/price_kind. Spot, USD-M,
COIN-M и trade/mark/index различаются уже в идентичностях. Первый сетевой
профиль обслуживает только Binance Spot trade OHLCV. Символы допускают
Unicode-буквы/числа в биржевом регистре, включая `币安人生USDT`; разделители,
невидимые символы и неявное преобразование регистра запрещены. HTTP query и
WebSocket/архивные URL используют UTF-8 percent encoding.

Каталог сохраняет base/quote, статус, шаг цены и количества, время наблюдения
и отдельно найденное первое доступное минутное открытие. Это наблюдаемая
граница истории, а не обещание точной юридической даты листинга. Запрос полного
exchangeInfo использует `showPermissionSets=false`: данные разрешений аккаунтов
не нужны публичному провайдеру и существенно увеличивают ответ.

История поддерживает 1/3/5/15/30/60/120/240/360/480/720 минут и D/W/M. Для
недели используется понедельник UTC, для месяца — реальная календарная длина.
Контекстное исполнение и live квалифицированы на перечисленных минутных
интервалах. Загрузка D/W/M не означает поддержку календарного replay.
Машиночитаемый контракт: `GET /api/market/capabilities`.

## 2. Единая загрузка истории

`fetch`, прежний `storage fetch` и HTTP используют `HistoryJobs`. Сетевые
запросы выполняет один фоновый I/O-поток. HTTP возвращает `202` и task_id.
Запрос закрепляет инструмент, диапазон, источник rest/archive и gap_policy.
Server time закрепляется один раз; end не должен быть позже него. Диапазон
`[start_ms,end_ms)` выбирает свечи по времени **открытия**. Закрытие проверяется
по данным биржи относительно закреплённого server time.

Ответы читаются по страницам до 1000 строк; примерно каждые 10000 свечей
публикуется Parquet и короткая транзакция фиксирует покрытие/курсоры задачи.
Память не растёт вместе со всем диапазоном. Уже записанные страницы не
загружаются повторно после падения. Незавершённая задача не становится
успешной из-за наличия этих страниц. Отмена сохраняет опубликованный префикс.
Running/interrupted-задачи восстанавливаются в queued при новом старте сервиса.
Failed/cancelled возобновляются явно. Параметры задачи при resume не меняются.

Одинаковые активные запросы получают один task_id. Один history worker
сериализует прочие загрузки. Общий HTTP governor ограничивает вес запросов,
учитывает `X-MBX-USED-WEIGHT-1M`, `429/418`, `Retry-After`, ограниченные повторы
и отменяемое ожидание. Невосстановимые 4xx не повторяются. Фоновая работа
ожидает ресурсный бюджет; HTTP при занятости отвечает `COORDINATOR_BUSY`.

Архив — явно выбранный отдельный источник. Месячный ZIP проверяется по
официальному SHA256, CRC, имени и размерам; CSV читается ограниченно. Начиная
с января 2025 Spot timestamps из микросекунд переводятся в миллисекунды.
REST/WS/archive имеют разные пространства источника. Нет автоматического
смешивания или утверждения, что один из них точнее TradingView. Если текущий
месячный архив ещё не готов, задача сообщает ошибку; можно выбрать REST.

## 3. Отчёт о покрытии

Запись «диапазон был получен» отличается от наличия всех свечей. Отдельный
`coverage-report.1` содержит:

- before_available — до первого наблюдаемого доступного интервала;
- not_closed — ещё открытый хвост;
- not_fetched — участок, который не был успешно получен;
- missing_candle — ожидаемое открытие отсутствует внутри полученного диапазона.

`confirmed_complete` проверяет закрытый доступный диапазон, `requested_complete`
учитывает также начало истории и открытый хвост. По умолчанию missing/not_fetched
дают failed. `allow_with_metadata` разрешает запуск с явным отчётом. Свечи
никогда не синтезируются. Отчёт ограничен 200 интервалами, сохраняет счётчики
и признак усечения. Refresh создаёт новую ревизию; старые снимки неизменяемы.

## 4. Общий живой поток и восстановление

Один физический WebSocket обслуживает подписчиков одного инструмента,
таймфрейма, поколения данных и реализации ingestion. Прогрев у каждой сессии собственный.
Сначала открывается сокет с ограниченным буфером, затем получается история,
после сверки обрабатываются накопившиеся сообщения. После разрыва повторяется
этот порядок с чтением последнего закрытого бара для проверки пересечения.

Неизменяемый raw journal содержит исходные сообщения и нормализованные
`candle-observation.1`, а также gap/recovery/diagnostic. Сохраняются время
открытия/закрытия свечи, время события биржи и локальное время получения.
Повторные, устаревшие и вытесненные подтверждённым REST-снимком сообщения
отмечаются явно; корректные входы не отбрасываются ради уменьшения очереди.

Открытая свеча может изменять close; open неизменен, high/volume не убывают,
low не возрастает. Изменение подтверждённого OHLCV при повторе или проверке
пересечения останавливает сессию. Требуется новый расчёт на новой ревизии:
`fresh_feed: true`, CLI `--fresh-feed` или «Новая ревизия потока и прогрева»
в вебе. Новая генерация получает отдельный raw journal/индекс подтверждений
и принудительно обновляет прогрев. Старые подтверждения не перезаписываются.
Реестр live_series направляет последующих обычных подписчиков в актуальную
генерацию; смена поколения не переподключает старые сессии к другой истории.
Полная периодическая сверка всей давней истории биржи не выполняется.

Восстановление REST возвращает закрытые свечи. Потерянная последовательность
обновлений внутри свечи не восстанавливается. Gap остаётся в журнале и UI.
Пропуски самих закрытых свечей по умолчанию останавливают сессию; разрешение
требует явного `allow_with_metadata`. Профиль не поддерживает varip или
стратегии calc_on_every_tick, поэтому пропущенные preview не подменяют
подтверждённое состояние исполнения.

## 5. Live → исполнение

Отдельный профиль `openpine.received-realtime.1` использует существующие IR,
runtime, rollback, брокер и replay storage. Старый `observed-realtime.1`
сохраняет собственные правила логических границ и порядка контекстов.

В received-профиле open означает **первое полученное накопленное состояние**
свечи. Оно может прийти внутри интервала. Время доступности равно максимуму
локального получения, предыдущей доступности и необходимой границы свечи;
исходные времена остаются в raw journal, коррекция локальных часов считается.
Close доступен после получения подтверждения биржи, а не задним числом на
границе интервала. Прогрев и восстановление поступают как явно сохранённые
close-only snapshots. Поддерживается один основной контекст на сессию.

Raw cursor, состояние преобразования и добавление нормализованных событий
в replay inbox фиксируются **одной SQLite-транзакцией**. Только после этого
конечный worker применяет пачку до 1000 событий. Все обновления исполняются,
preview на экране заменяется; в постоянные выходы попадают только close.
Worker разделяет общий бюджет с историческими вычислениями. Падение
повторяет тот же сохранённый входной префикс, до трёх попыток; затем нужно
явное продолжение. Последний совместный checkpoint остаётся доступен.

Брокер — симулятор: стратегия рассчитывается на close, pending market-заявки
моделируются по open следующего бара OHLCV. Это не отправка ордеров на биржу
и не обещание исполнения по цене, доступной в момент получения сообщения.
Шаги цены/количества для новой стратегии берутся из закреплённых метаданных
инструмента либо передаются явно.

Сессия закрепляет хеш реализации преобразования, нормализации и live application,
метаданные инструмента и политику пропусков. После изменения этой реализации
нужна новая live-сессия. Старые raw/replay журналы и результаты сохраняются.

## Хранение, пределы и обслуживание

Миграция SQLite **5** добавляет market_instruments, data_tasks/data_pages,
live_feeds/live_observations/live_parts, live_closed и live_sessions. Старые
задания, снимки, checkpoint и replay сохраняются. data_pages удерживает
происхождение опубликованных страниц вместе с task/as_of.
Миграция **6** добавляет live_series и сохраняет ссылки на уже существующие
генерации. Текущая версия каталога — 6.

Raw payload архивируется по 10000 записей в Parquet; SQLite сохраняет хеши
и курсоры. Подтверждённые live-свечи хранятся небольшим SQLite-хвостом и
переносятся в общий CandleStore блоками по 1000, также при штатном закрытии.
Индекс closed-свечей позволяет читать окно без полного прохода по ленте.
Backup/restore и reachability учитывают новые ссылки. Prune пока сохраняет
историю data_tasks и live_sessions, вместе с удерживаемыми ими снимками.

Пределы первого профиля: 32 активных history-задачи, один history I/O worker,
два физических WebSocket, восемь активных сессий. Library buffers ограничены
16 кадрами по 64 KiB. Отставание подписчика более 10000 raw-записей включает
backpressure; нет тихого отбрасывания. Пять последовательных ошибок подключения
требуют явного resume. Нет сообщений 30 секунд — разрыв и восстановление.

Исторический запрос ограничен 10 миллионами баров; для минутных интервалов
проверяется также потенциальная ширина диапазона до учёта листинга. Очень
ранний start следует сузить. Время задачи — до часа, каждый HTTP запрос — до
10 секунд. Raw journal и нормализованный replay ограничены 10 миллионами
записей/событий; для длительной эксплуатации нужны новые сессии/хранилища.
Лимиты compute-процессов/памяти/потоков остаются общими и не увеличены.

## 6. Запуск и веб

```sh
python -m pip install .
python -m apps.openpine serve --port 8765
```

На веб-панели: исходник → инструмент/интервал и число баров прогрева →
«Наблюдать». Каталог и прогрев загружаются фоновыми задачами. Видны соединение,
очереди источника/исполнения, gap, предварительная свеча и ограниченное окно
выходов. Текущая свеча заменяется по её времени. Есть выбор сохранённой сессии,
stop/resume и окна графика/журнала симуляции.

CLI использует те же сервисы:

```sh
python -m apps.openpine fetch --provider binance --symbol BINANCE:BTCUSDT --timeframe 60 --start-ms 1704067200000 --end-ms 1704153600000 --output btc.json
python -m apps.openpine market catalog refresh
python -m apps.openpine market catalog list --query BTC
python -m apps.openpine market live run --source examples/pipeline/v6.pine --symbol BINANCE:BTCUSDT --timeframe 1 --warmup-bars 1000 --duration 60
python -m apps.openpine market live status --id SESSION_ID
python -m apps.openpine market live resume --id SESSION_ID --duration 60
python -m apps.openpine market live chart --id SESSION_ID --start 0 --limit 500
```

`--artifact` принимает исторический IR. `--request` — закрытый JSON запроса
для автоматизации. В live request input_ref должен принадлежать этому store.
`market history run/submit/status/resume/cancel/list` работает с request-файлом.
Submit сохраняет задачу; фоновая работа живёт в процессе сервера/CLI. Run ждёт
завершения. CLI live run/resume работает указанную duration и сохраняет stop;
остановка может оставить принятый, ещё не исполненный префикс для продолжения.
Одним каталогом одновременно владеет один процесс приложения.

Экспорт до 100000 баров содержит переносимый JSON. Больший экспорт — манифест
с Parquet-ссылками; для него нужно сохранять каталог и файлы объектов.

HTTP с прежними Host/Origin/token-проверками:

- `GET /api/market/capabilities`, `/instruments?q=BTC&limit=100`;
- `POST /api/market/catalog/refresh` с `{}`;
- `POST /api/market/history` с HistoryRequest, `GET /history/ID`,
  `POST /history/ID/cancel` или `/resume` с `{}`;
- `POST /api/market/live` с input_ref, instrument, timeframe, start_ms,
  broker_settings, timeout_seconds и необязательными gap_policy (по умолчанию fail)
  и fresh_feed (по умолчанию false);
- `GET /api/market/live`, `/live/ID`, `/live/ID/chart`, `/ledger`, `/journal`;
- `POST /api/market/live/ID/stop` или `/resume` с `{}`.

Chart/ledger ограничены 5000 строками, raw journal — 1000; start/limit задают
продолжение. Прежний `POST /api/snapshots` для Binance теперь возвращает `202`
и task_id; upload/demo сохраняют синхронный ограниченный путь.

## 7. Приёмка

`test_marketdata`, `test_live_market`, `test_market_http` проверяют контракты,
Unicode, календарные границы, Retry-After, сохранённые страницы, строгую
полноту, ожидание бюджета, отмену, ENOSPC, настоящие локальные WebSocket,
нескольких подписчиков, разрыв/REST repair, атомарный raw/replay cursor,
настоящий kill worker, backup/restore, GC/prune и Pine v1–v6.

```sh
python -m tools.release_gate
python -m tools.install_check
python -m tools.market_benchmark --directory ../market-100k --bars 100000 --kill-after 30000
python -m tools.market_benchmark --directory ../market-1m --bars 1000000 --kill-after 300000
python -m tools.market_benchmark --directory ../market-10m --bars 10000000 --kill-after 3000000
```

Benchmark требует новый каталог. Данные синтетические; координатор действительно
завершается, после открытия того же store продолжаются его курсор/as_of и
проверяется весь результат. Публичные REST/WS отдельно проверяются ограниченными
сетевыми smoke-тестами. Сводка приёмки: [evidence/marketdata-20261022.json](evidence/marketdata-20261022.json).

Использованы выбранные идеи прежних провайдеров: инструмент/рынок, каталог,
календарь, первый доступный бар, отчёт о покрытии, shared fetch и live normalization.
Зависимостей от старых пакетов, их Bar, EventBus, кешей и store не добавлено.
Алгоритмы, возвращавшие частичный успех или терявшие intrabar-события, не перенесены.

Официальные описания: [Spot REST](https://github.com/binance/binance-spot-api-docs/blob/master/rest-api.md#exchange-information),
[поток свечей](https://developers.binance.com/docs/binance-spot-api-docs/web-socket-streams),
[архивы, checksums и единицы времени](https://github.com/binance/binance-public-data#data-information),
[WebSocket client](https://websockets.readthedocs.io/en/stable/reference/sync/client.html).
