# Воспроизводимая сессия R6

Пакет `openpine.session-recording.1` содержит исходник/Typed IR, настройки,
контексты, снимки прогрева и восстановления, raw journal, нормализованные
события и логические хеши подтверждённых выходов/сделок. Это каталог с
контрольным manifest и неизменяемыми объектами по SHA-256. Пакет не зависит
от исходного state directory и не содержит исполняемого Python/pickle.

Перед экспортом остановить сессию. Экспортируется **опубликованный префикс**,
включая его preview. Уже принятый, но ещё не исполненный хвост в расчёт не
входит; `accepted_tail_excluded` показывает его размер. Общий raw-поток может
содержать более поздние записи другого подписчика; их cut указан отдельно.
Пакет сохраняет эти записи для аудита, а исполнение использует закреплённый
нормализованный префикс. Export не подменяет journal checkpoint копией файлов.

```sh
python -m apps.openpine market live stop --id SESSION --state-dir .runtime/jobs
python -m apps.openpine market live export --id SESSION --state-dir .runtime/jobs --bundle ../recording
python -m apps.openpine market recording verify --bundle ../recording --state-dir ../verification
python -m apps.openpine market recording replay --bundle ../recording --state-dir ../offline --batch-size 1000
```

Destination экспорта должен быть новым и находиться вне рабочего store.
Проверка хешей/последовательностей выполняется до создания replay. В новом
store запускается прежний изолированный worker с закреплённым IR. Сеть для
воспроизведения не нужна. Размер пакета вычисления может меняться: сравниваются
упорядоченные значения, журнал брокера, контексты и preview, а не физическое
разбиение Parquet. Несовместимый IR/профиль явно отклоняется.

`test_recordings` проверяет переносимость исходника/IR, прогрев, исходный raw,
стратегию/индикатор, пакеты 1 и 1000, запрет сети, повреждение объектов и
отклонение импорта до создания replay. Общая приёмка после всех семи пунктов
описана в [плане](LIVE_CONTINUITY_PLAN.md).

## Общий UTC-календарь

`packages.contracts.calendar` определяет открытия/закрытия, сдвиги и допустимые
пары контекстов для провайдера, исторического планировщика и обоих replay.
D — сутки UTC, W — понедельник, M — первый день следующего настоящего месяца.
Месяц никогда не заменяется фиксированным числом миллисекунд. Пропущенные
свечи сохраняются пропущенными; календарь не выполняет ресемплинг.

Фиксированные минутные запросы сохраняют правило точной кратности. Минутный
primary для календарных запросов должен делить сутки. D/W/M допускают тот же
или старший календарный интервал. При W→M граница месяца может находиться внутри
недели: availability вычисляется по настоящим границам закрытия/открытия.
Весь профиль ограничен UTC/24x7, без неявного выбора часового пояса/торговой сессии.

Выпуск `pine-requests-20261022.2` закрепляет эти решения отдельно от прежнего
неизменяемого выпуска. Версионные defaults/lookahead v1–v6 сохранены. Тесты
охватывают високосный февраль, понедельник, неделю через границу месяца,
историческую доступность и восстановление по всем версиям.

## Несколько live-контекстов

Профиль `openpine.received-realtime.2` допускает один основной и до семи
дополнительных контекстов. Literal-запросы `security` / `request.security`
автоматически определяют необходимые инструменты и интервалы. Можно передать
`contexts` явно: список `context_id`, `instrument`, `timeframe`, `start_ms`.
Каталог должен содержать торговые метаданные всех инструментов.

Все подписчики одного источника разделяют физический поток. Суммарный предел —
восемь потоков и восемь сессий; вычислительные бюджеты не увеличены. SQLite
миграция 7 добавляет `live_bindings` и `live_arrivals`. Raw append и глобальный
arrival ordinal фиксируются одной транзакцией. Старые одноконтекстные записи
сохраняют локальный порядок; миграция не утверждает неизвестный исторический
порядок между прежними независимыми потоками.

Прогрев закрепляет общий server time и объединяет закрытые свечи по настоящей
границе закрытия; дополнительные контексты на совпавшей границе идут перед
primary. Затем используется сохранённый порядок получения raw. У каждого
источника собственные warmup/repair/mapper/cursor; публикация всего графа и
нормализованного inbox выполняется одной транзакцией. Stop освобождает все
подписки этой сессии, оставляя подписки других потребителей.

Значение старшего контекста должно быть уже получено и соответствовать времени
основной свечи. Для запоздавшей primary сохраняются последние 4096 закрытых
значений каждого написанного запроса. Выход за этот горизонт требует пересчёта
из записи; будущая свеча не подставляется вместо недоступной старой. Потерянные
intrabar-обновления после разрыва по-прежнему не восстанавливаются из REST.
Сбой публикации оставляет прежние совместные курсоры; временный сбой storage
можно продолжить явно. Старые реализации профиля не продолжаются с другой
семантикой: их журналы/результаты сохраняются, новая сессия получает новый pin.

`test_live_contexts` проверяет все версии на запоздавшей primary, три таймфрейма
1/5/60, общие источники двух сессий, global arrival order, атомарность при отказе
диска, backup/restore и офлайн-воспроизведение графа.

## Конечный пакетный worker

Фоновая проекция подготавливает ограниченный inbox каждой сессии и запускает
один конечный worker для группы до восьми replay. Он один раз загружает
неизменяемую спецификацию/каталоги, затем создаёт свежие runtime, sink и broker
для каждого ID. Контрольные точки публикуются отдельно; отказ одного ID не
теряет подтверждённые префиксы остальных. Рабочие процессы, потоки и память
учитываются прежним общим бюджетом. Idle-процессы за сессиями не закрепляются.

В одном обходе — до 1000 событий на сессию; новые нормализованные входы
притормаживаются при 2000 ожидающих событий. Parent контролирует heartbeat,
таймаут текущей сессии, отмену и RSS процесса. После смерти parent конечный
worker завершается. Повторная попытка восстанавливает только durable checkpoint.
CPU, wall time, запуски worker и максимальная выборка RSS сохраняются отдельно
от вычислительного результата в `settings/live_execution_metrics`.

Замер восьми простых индикаторов / трёх поступлений (48 событий): 80,401 секунды
и 24 запуска по одному replay против 12,245 секунды и 3 групповых запусков.
p95: 26,791 → 4,043 секунды; child CPU: 73,656 → 11,359 секунды. Хеши всех
логических выходов совпали. Это измерение диспетчеризации маленьких расчётов;
оно не является оценкой производительности тяжёлого Pine. RSS — максимум
периодических выборок, не гарантированный абсолютный пик. Протокол:
[evidence/live-dispatch-20261022.json](evidence/live-dispatch-20261022.json).

`test_replay_batch` проверяет смешанные версии и стратегии, изоляцию отказа,
равенство с отдельными свежими engines, отмену до запуска и общий бюджет.
`tools.live_benchmark --directory ../dispatch --sessions 8 --rounds 3`
воспроизводит сравнение; требуется новый каталог и Python 3.14.8.

## Сегменты и хранение

Raw и нормализованная лента автоматически закрывают Parquet-сегменты по 10000
записей. Принудительная ротация запечатывает и неполный хвост по фиксированному
cut. Следующий сегмент продолжает тот же 64-битный sequence и hash chain;
checkpoint runtime/broker не сбрасывается. Общий предел в десять миллионов
событий снят. Ограничение одной команды исполнения и исторического снимка
остаётся отдельным. Размеры пакетов, состояния и памяти сохраняют свои бюджеты.
Отсутствующий сегмент с очищенным SQLite payload вызывает ошибку, а не ожидание
или пропуск входов. Конкурирующая компактация проверяет публикацию того же cut.

```sh
python -m apps.openpine market maintenance rotate --state-dir .runtime/jobs
python -m apps.openpine market maintenance segments --state-dir .runtime/jobs
python -m apps.openpine market maintenance preview --state-dir .runtime/jobs --before-ms CUTOFF
python -m apps.openpine market maintenance apply --state-dir .runtime/jobs --before-ms CUTOFF --preview-id SHA256
```

Retention выбирает старые остановленные сессии, принадлежащие им replay и
источники без других подписчиков. Preview перечисляет кандидатов и размер
освобождаемых файлов. Apply требует тот же cutoff/grace и актуальный preview ID;
изменившийся план отклоняется. Активные jobs/history/live/worker блокируют apply.
Экспорт удерживает per-replay lease, поэтому его данные не удаляются посреди
копирования. Каталог удалённых ссылок публикуется перед удалением файлов;
прерывание оставляет только безопасные orphan-файлы для следующего обслуживания.

За один проход — до 1000 сессий/источников и 10000 файлов; `truncated` требует
следующего preview. Снимки свечей, coverage, input pins и оставшиеся сессии
сохраняются. Их отдельные правила обслуживания описаны в [STORAGE.md](STORAGE.md).
SQLite получает свободные страницы для повторного использования; автоматический
VACUUM и обещание уменьшения размера файла каталога не выполняются. Новый поток
после удаления прежнего получает новую generation, сохраняя уникальность истории.
Экспортированные пакеты самостоятельны и продолжают работать после retention.

HTTP: `GET /api/market/storage/segments`, `POST /api/market/maintenance/rotate`
с `{}`, `/preview` с `before_ms, grace_seconds`, `/apply` с теми же полями и
`preview_id`. Сохраняются прежние проверки token/Host/Origin.

## Веб-обзор

Карточки live-контекстов показывают основной и запрошенные интервалы, прогрев,
подтверждённые свечи, очередь каждого источника, последнее получение и ошибки.
Обзор «Данные и потоки» содержит страницы снимков и блоков, диапазоны UTC,
число свечей, размеры, отчёты покрытия, подписчиков и переподключения.
Отсутствие отдельного отчёта не выдаётся за полное покрытие. Размеры файлов
подсчитываются без проверки всех хешей; это обзор, а не аудит целостности.

`GET /api/market/storage?start=0&limit=50` ограничивает страницу ста записями.
SQLite schema 8 добавляет индексы страниц и поиска отчёта по snapshot ID;
миграции старых каталогов сохраняют данные. Обслуживание требует сначала
preview; изменение срока хранения отменяет прежний отчёт. Активная работа
блокирует удаление, а применение требует подтверждения перечисленного плана.

Проверено через HTTP и браузер на публичном Binance Spot: один скрипт с
контекстами 1/5/60 минут, прогрев 180 основных свечей, графики и preview,
обзор сохранённых диапазонов и запрет удаления при активном наблюдении.

## Сквозная приёмка непрерывности

```sh
python -m tools.session_soak --directory ../session-acceptance --minutes 1440
```

Команда требует новый каталог и Python 3.14.8. Шесть сессий Pine v1–v6
разделяют три потока 1/5/60 минут; чётные версии исполняют стратегии.
Синтетическая биржа задаёт независимую модель OHLCV. После прогрева на двух
часах поступают сутки модельных данных, включая потерянную свечу, gap и REST
reconciliation. Исходные внутрисвечные обновления потерянной свечи не выдумываются.

Приёмка убивает настоящий процесс координатора с опубликованным checkpoint,
ожидающими событиями и ещё не спроецированным raw-хвостом. Затем убивает
групповой worker после первой новой публикации, запечатывает неполные журналы,
восстанавливает резервную копию в новый каталог и продолжает все сессии.
Проверяются все значения close и двух запрошенных close по независимой модели,
финальный preview индикаторов и отсутствие intrabar-исполнения стратегий.
Сессии экспортируются и повторяются офлайн в отдельных новых хранилищах;
сравниваются хеши всех рядов, торгового журнала, контексты и состояние брокера.

`report.json` разделяет `model_minutes` и фактические `wall_seconds`.
Это ускоренная проверка непрерывности на записанных входах. Она не утверждает
сутки ожидания реальной биржи, максимальную пропускную способность или точное
соответствие TradingView. Короткий двухчасовой вариант v1/v6 включён в gate.
Installed-wheel smoke отдельно проверяет три контекста, групповой запуск,
UTC-календарь, обзор, ротацию и офлайн-пакет вне исходной репы.

Retention учитывает и OS lease оставшегося после смерти координатора replay
worker: пока child не завершён, новый владелец каталога не удалит его данные.

Приёмка 22 октября 2026: 1440 модельных минут и 120 минут прогрева,
шесть версий / три общих источника; 615,840 секунды реального исполнения.
Проверены 28080 значений по независимой модели. Все шесть офлайн-повторов
совпали по всем рядам, торговым журналам и логическому состоянию. После
ротации сохранены 3 raw-сегмента и 12 сегментов событий без незапечатанных
хвостов. Подробный протокол: [evidence/session-continuity-20261022.json](evidence/session-continuity-20261022.json).

После Linux CI подготовка аварийной точки сделана независимой от скорости
runner: ровно 16 raw-записей на сессию вместо временного бюджета `tick`.
Перед kill сохраняются число ожидающих событий и оставшийся raw-хвост;
при раннем выходе coordinator его traceback попадает в CI log. Повторная
локальная проверка v1/v6 прошла с 16 pending events и 251 raw records на каждую
сессию. Протокол: [evidence/session-cut-20261022.json](evidence/session-cut-20261022.json).
