# Расчёт Pine на полученных обновлениях

`openpine.observed-calculation.1` добавляет расчёт скрипта на каждом принятом
основном ценовом событии. Порядок закреплён в `spec/intrabar-profile.json`:
цена → исполнения существующих заявок → расчёт Pine → новые команды.
Используются прежние Binder, Typed IR, evaluator, брокер, worker и хранилище.
Модель описывает записанные обновления; точное сравнение с TradingView отдельно.

## Версии и выбор режима

| Возможность | v1 | v2–v3 | v4–v6 |
| --- | --- | --- | --- |
| Явный режим OpenPine в replay/live | Реконструкция с явным выбором | Да | Да |
| `strategy(..., calc_on_every_tick=true)` | Диагностика отсутствующего свидетельства | Да | Да |
| `varip` скаляров и примитивных массивов | Диагностика | Диагностика | Да |

Параметр заголовка найден в закреплённом справочнике с v2, ключевое слово
`varip` — с v4. Ссылки на конкретные записи и их контрольные суммы входят
в профиль. Поддержка всего остального Pine из наличия этих записей не следует.

Новый заголовок использует экономическую сигнатуру и её ограничения. В replay
он автоматически закрепляет наблюдаемый брокер; это действует и при явном
`calc_on_every_tick=false`, который сохраняет расчёт стратегии на закрытии.
Прежние заголовки без нового параметра сохраняют прежний выбор профилей.

Для стратегии `true` включает новый режим, `false` запрещает противоречащий
явный выбор режима. Без параметра режим можно выбрать через конфигурацию.
Индикатор с `varip` включает профиль автоматически. Стратегия с одним `varip`
без выбора режима продолжает рассчитываться на закрытии бара.

## Состояние и история

Каждый промежуточный проход использует ветку последнего подтверждённого
runtime. Обычные переменные, `var`, числовая история, состояния TA и функций
откатываются к этому рубежу. Накладки на кольцевые буферы сохраняют ограниченную
память; подтверждённая история целиком на каждом обновлении не копируется.

`varip` инициализируется при первом достигнутом выполнении объявления и
сохраняется между обновлениями. Автоматического сброса при открытии нового
бара нет: для этого скрипт может использовать `barstate.isnew`.
Локальные значения принадлежат своему месту вызова и контексту.

Поддерживаются int/float/bool/string и массивы этих примитивов в рамках
существующего типового и ресурсного профиля. Объекты, достижимые через
`varip`-ссылки, сохраняют изменения; алиасы остаются согласованными.
Обычные массивы используют прежний rollback. Временные идентификаторы новых
массивов уплотняются относительно подтверждённой кучи, поэтому число
промежуточных обновлений не расходует пространство подтверждённых объектов.

На close проходит один завершающий расчёт с сохранёнными `varip`-значениями.
История и постоянные выходы фиксируются один раз на бар. Preview содержит
предварительные выходы, revision и время доступности последнего основного
наблюдения. Чтение статуса и восстановление сами не запускают новый проход.

Выражения `security/request.security` имеют собственные runtime и `varip`.
Каждое выражение рассчитывается один раз на своё принятое обновление.
Повторные чтения из основного контекста используют сохранённый preview и
сохраняют прежние ограничения времени, gaps, lookahead и доступности данных.

## Заявки и восстановление

Новая команда становится доступной на следующем основном наблюдении, включая
следующее обновление той же свечи. Отмена после исполнения на текущей цене
не отменяет состоявшуюся сделку. Pending, изменение, защита, OCA, trailing,
комиссии и риск используют общий брокер. Размер новой заявки рассчитывается
по известной цене и капиталу в момент создания команды.

Команды и их последовательность сохраняются вместе с брокером. До закрытия
свечи брокер принимает командные пачки, сохраняя число подтверждённых баров.
Внешние координаты сделок остаются координатами свечи; observation provenance
показывает фактический sequence/revision и время доступности ценового кадра.

`openpine.replay-state.3` дополнительно сохраняет количество проходов,
последнее основное событие, `varip`-корни, предварительные выходы и состояние
каждого запроса. `openpine.replay-config.4` закрепляет выбранный режим.
Новый worker проверяет типы, принадлежность переменных, ссылки, курсоры и
согласованность брокера. SQLite атомарно публикует общий input cursor,
контрольную точку и префикс выходов/журнала. Схема SQLite остаётся прежней.

Запись `openpine.session-recording.3` сохраняет конфигурацию и включает
состояние расчёта в проверяемый логический результат. Офлайн replay проверяет
равенство preview, количества проходов, подтверждённых рядов и журнала.

## Запуск

В `examples/intrabar` находятся 27 собственных программ, пять лент обновлений
и явные ожидаемые результаты. Контекстный файл выбирает профиль, поэтому
пример v1 работает без неподтверждённого параметра Pine.

```sh
openpine replay create --source examples/intrabar/v6-commands.pine --contexts examples/intrabar/contexts.json --calculation-profile observed
openpine replay append --id ID --events examples/intrabar/commands.ndjson
openpine replay advance --id ID --max-events 3 --checkpoint-every 1
openpine replay advance --id ID
```

HTTP replay/live принимает `calculation_profile: "openpine.observed-calculation.1"`.
В вебе режим выбирает флажок «Рассчитывать скрипт на полученных обновлениях».
Заголовок скрипта также учитывается при создании; фактический режим показывается
в сохранённой сессии и закрепляется на её время жизни.

В этом профиле `calc_on_order_fills` и `process_orders_on_close` не добавлены;
они реализованы отдельным [профилем фаз стратегии](STRATEGY_CYCLE.md). Здесь неизвестные тики и сигналы в пропущенных обновлениях не
восстанавливаются. Исторические одиночные close дают по одному проходу.
Версионные ограничения Pine и несовместимость implementation identity
продолжают проверяться. [План приёмки](INTRABAR_PLAN.md).
