# Наблюдаемые события и офлайн replay R6

Первый профиль `openpine.observed-realtime.1` работает с записанными обновлениями
свечей на Python 3.14.8. Он использует существующие Typed IR, Binder, series-ядра,
брокер и Parquet sink. Это локально определённая модель по закреплённым
артефактам. Точное соответствие TradingView остаётся отдельной приёмкой.

## Шесть частей

1. Закрытый контракт `market-event.1`: глобальный sequence, context_id, вид
   open/update/close, время открытия, время доступности, revision и полные
   накопленные OHLCV. Время — UTC миллисекунды, цены положительны.
2. Индикатор пересчитывается на каждом наблюдаемом обновлении. `var`, состояния
   EMA/SMA/change/cross и история берутся от последнего подтверждённого бара.
   Временная ветка использует накладки над кольцевыми буферами: полная история
   на каждом update не копируется. Только close изменяет подтверждённый runtime
   и попадает в постоянный ряд. Preview всегда помечен `confirmed: false`.
3. Основной и дополнительные контексты следуют одному журналу доступности.
   Поддерживаются прежние close/EMA-запросы, фиксированные минутные интервалы,
   тот же/старший кратный таймфрейм и максимум восемь контекстов.
4. Стратегия рассчитывается на close, pending market-заявки исполняются на
   следующем наблюдаемом open. Повторное обновление не создаёт новую заявку.
   Временные fills текущего бара входят в подтверждённый торговый журнал при
   close. До этого они воспроизводятся из сохранённого open и состояния брокера
   на предыдущем close. Это обеспечивает продолжение внутри открытой свечи.
5. SQLite inbox сохраняет событие до исполнения. Полезная нагрузка архивируется
   блоками по 10000 событий в Parquet/ZSTD; sequence/hash остаются в каталоге
   для проверки старых повторов. Checkpoint объединяет runtime, состояния
   запросов, активные свечи, брокер и префикс выходов. Все файлы публикуются до
   короткой транзакции, которая атомарно меняет applied cursor и ссылки.
6. CLI/HTTP исполняют конечный префикс в отдельном worker. Он разделяет общий
   лимит процессов/потоков/памяти с историческими заданиями, наблюдает за смертью
   координатора, ограничен timeout/RSS и публикует heartbeat. Новый процесс
   продолжает последний опубликованный префикс. Backup/restore/GC удерживают
   конфигурацию, IR, входной журнал, checkpoint, графики и сделки. GC удаляет
   оставшиеся после падения рабочие файлы только после освобождения lease
   дочернего процесса.

## Время, повторы и ошибки

Sequence начинается с нуля и не имеет дыр. Одинаковый sequence с тем же payload
идемпотентен, включая повторы уже архивированного события. Другой payload с тем
же sequence отклоняется. Новая свеча начинается с revision 0; очередное update
или close должно иметь revision +1. Open неизменен, high/volume не уменьшаются,
low не увеличивается. Пропуски свечей сохраняются; пропуски событий/revision
требуют недостающего префикса. Закрытые свечи неизменяемы: исправления требуют
нового replay. Неподдержанная коррекция не применяется молча.

Open доступен в момент открытия, update — внутри интервала, close — ровно на
его правой границе. Входной журнал уже должен быть упорядочен по доступности;
при равном времени закрытия/обновления дополнительных контекстов предшествуют
закрытию основного, затем идут открытия следующего интервала. Внутри одной
группы порядок задаёт sequence. Опоздавшее событие не меняет прошлый результат.
Для исторической загрузки разрешён одиночный close с revision 0 без open.

Append атомарен в пределах одной пачки. Длительный CLI импорт фиксирует пачки
по 1000: при ошибке ранее принятые пачки сохраняются и могут быть повторены.
Принятие в inbox означает сохранность входа; `sequence` в статусе отдельно
показывает реально исполненный префикс. Ошибка вычисления оставляет предыдущий
checkpoint доступным. Неверный принятый хвост не пропускается; для его изменения
создаётся новый replay.

## Версии и границы

`spec/replay-profile.json` фиксирует отдельные профили v1–v6, хеши исходных
каталогов и существующего spec lock. `tools.replay_spec --check` проверяет их в
общем gate; файл и runtime/rollback входят в execution identity. Старые
исторические семантические bundles не переписаны.

Имена API, seed EMA, NA, логика и переменные сохраняют существующие версионные
правила и оговорки реконструкции. Для наблюдаемого потока оба lookahead-режима
используют только уже полученные данные: при gaps_off доступно наблюдаемое
развивающееся значение текущего дополнительного бара, при gaps_on — новое
подтверждённое значение. Историческая подстановка будущего из lookahead_on
сюда не переносится. Поэтому равенство с историей проверяется для одного
контекста либо для ленты из одних close с явно заданным lookahead_off.
Закрытие основного бара само по себе не подтверждает старший таймфрейм:
его наблюдаемое развивающееся значение может отличаться от готовой истории
даже при lookahead_off. Этот случай отдельно проверяется как observed replay.

Не входят в этот профиль: сетевой WebSocket-провайдер, экран управления replay,
varip/barstate, calc_on_every_tick, calc_on_order_fills, limit/stop, lower-TF,
календари бирж, произвольные выражения запросов и исправление закрытой истории.
Живой провайдер и отображение незакрытой свечи подключаются после этой модели.

## Запуск

В `examples/replay` находятся собственные синтетические OHLCV-события,
контексты, индикаторы и стратегии v1–v6.

```sh
python -m apps.openpine replay create --source examples/replay/v6-indicator.pine --contexts examples/replay/contexts.json --state-dir .runtime/replay
# Подставить replay_id из ответа следующих команд:
python -m apps.openpine replay append --id ID --events examples/replay/tape.ndjson --state-dir .runtime/replay
python -m apps.openpine replay advance --id ID --max-events 4 --state-dir .runtime/replay
python -m apps.openpine replay status --id ID --state-dir .runtime/replay
python -m apps.openpine replay advance --id ID --state-dir .runtime/replay
python -m apps.openpine replay chart --id ID --start 0 --limit 100 --state-dir .runtime/replay
python -m apps.openpine replay ledger --id ID --start 0 --limit 100 --state-dir .runtime/replay
```

`create` также принимает `--artifact`. Существующий replay закрепляет вход,
контексты, broker settings и ресурсный профиль; при продолжении они не меняются.
Артефакт из другой execution identity требует новой компиляции и нового replay.

HTTP использует прежний loopback server и X-OpenPine-Token:

- `POST /api/replays`: input_ref, contexts, primary_id, broker_settings (null
  или прежний закрытый BrokerSettings), timeout_seconds.
- `POST /api/replays/ID/events`: `{ "events": [market-event.1, ...] }`, до
  10000 событий в пачке и общего ограничения тела HTTP.
- `POST /api/replays/ID/advance`: `{ "max_events": 10000,
  "checkpoint_every": 1000 }`. Конечная синхронная операция в worker; при
  занятом бюджете возвращается COORDINATOR_BUSY. Checkpoint позволяет дробить
  длинную ленту на вызовы.
- `GET /api/replays/ID`, `/chart?start=0&limit=100`, `/ledger?start=0&limit=100`.
  График и журнал ограничены 5000 строками; `next` задаёт продолжение.

Разбиение Parquet зависит от границ публикации; равенство результатов проверяется
по упорядоченным значениям/событиям и брокерскому учёту, а не по именам файлов.
Checkpoint и указатели выходов публикуются вместе, поэтому непринятый хвост
после падения не читается как подтверждённый результат.

## Проверки

`tests/test_realtime.py` проверяет все версии, состояния ядер и переменных,
каждую границу событий, совместное восстановление с запросами и брокером,
причинность, повторную доставку, архив, GC/backup/restore, ENOSPC, настоящий
kill worker, общий бюджет и CLI/HTTP. `tools.replay_benchmark` дополняет это
большой записанной лентой и реальным падением CLI-координатора:

```sh
python -m tools.replay_benchmark --directory ../replay-proof --bars 100000
python -m tools.release_gate
python -m tools.install_check
```

Gate запускает тестовые модули в отдельных процессах: глобальные фикстуры одного
модуля не должны расходовать рабочий лимит координатора следующего. Сам лимит
координатора и воркеров не увеличен.

Локальная большая приёмка: 100000 свечей / 300000 событий, 200000 значений
графиков и 349998 событий брокера. После паузы внутри свечи, backup/restore и
реального kill координатора совпали хеши всех упорядоченных выходов и учёт
брокера; рабочие файлы погибшей попытки удалены через GC. Отдельный индикатор
прошёл те же 300000 событий с var, EMA, SMA и историей. Его checkpoint с большой
SMA-историей — 33748901 байт; стратегия с EMA — 2276 байт. Размер состояния
зависит от используемых конструкций. Проверены 22 сценария replay и чистая
установка с CLI/HTTP v1/v6. Протокол и точная build/execution identity:
[evidence/replay-20261021.json](evidence/replay-20261021.json).

Регрессионная приёмка: 296 unit-тестов общего прогона и один дополнительный
совместный тест (108 границ v1–v6); 431 случай конформанса. Отчёты обновлены
под execution identity без изменения наблюдаемых результатов и проверены
также из заново установленного wheel вне checkout.
