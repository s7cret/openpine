# ADR-0085. Наследование рынка во вложенном запросе

Дата 2026-11-21. Статус принят для динамического профиля OpenPine R6.

Внутри выражения другого запроса пустой символ и `syminfo.tickerid` обозначают инструмент внешнего запроса. Аналогично пустой интервал и `timeframe.period` берут интервал снаружи. Поэтому при ротации A → B → A внутреннее `close[1]` на последнем шаге должно читать предыдущую свечу A. Это трактовка руководства для динамических запросов v5/v6. Сравнение результатов с работающим TradingView остаётся отдельной проверкой. [Руководство Pine](https://www.tradingview.com/pine-script-docs/concepts/other-timeframes-and-data/#nested-requests)

Сохранённый IR содержит каждый написанный вызов. При подготовке прямой цепочки из двух или трёх уровней OpenPine проверяет каждую пару аргументов отдельно. Если обе оси унаследованы или буквально совпадают с внешними, каждый уровень получает одну и ту же свечу. Для обычного внутреннего `security` с исходными настройками объединения достаточно выполнить конечное выражение в приватном состоянии внешнего рынка. Открывать второй курсор к тем же свечам в этом случае избыточно. В `job --plan-only` граф сохраняет идентификаторы вложенных вызовов, обе разрешённые оси и поля, полученные по наследованию.

Разные инструменты, несовпадающие интервалы, отдельный внутренний пересчёт валюты и разные окна прогрева требуют независимого расчёта. Для них текущий профиль возвращает `REQUEST_SCOPE`. Для внешнего `security_lower_tf` доступно выражение, вычисляемое по одной младшей свече, например `close`. Состояние внутренней EMA потребовало бы учёта свечей до начала ограниченного окна. Пересмотреть границу при реализации отдельного планировщика внутренних окон.

На двухминутном графике пример с минутными свечами A получает суммы 22, 30 и 38. В примере с тремя рынками и тремя уровнями предыдущие цены равны na, 30, 70, 16, 66 и 36. Для обоих проверяется полное совпадение результатов непрерывного и возобновлённого worker. [Сценарии](../../examples/dynamic-requests)
