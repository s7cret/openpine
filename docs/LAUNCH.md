# Подготовка запуска из приложения

Сервер сохраняет конфигурацию до загрузки истории. `Launches` использует
существующие HistoryJobs, CandleStore, Preparation, RunPlan и JobManager.
Дополнительных очередей, исполнителей и копий IR нет. SQLite migration 13
добавляет неизменяемую конфигурацию подготовки и ссылку на объект готового плана.

После компиляции приложение показывает контексты из `security` / `request.security`.
Основные и дополнительные данные можно загрузить из файлов OHLCV JSON или выбрать
из сохранённых снимков. Для поддержанных интервалов Binance Spot доступен
существующий REST/архивный провайдер. Сетевые ограничения провайдера не ограничивают
допустимые интервалы файловых снимков: например, примеры используют 4 минуты.
Контексты сопоставляются по symbol/timeframe; неоднозначные, лишние и отсутствующие
источники отклоняются до исполнения. Свечи автоматически не пересчитываются.

Кнопка «Подготовить запуск» закрепляет настройки, снимки и план. Покрытие проверяется
для каждого источника, включая края явно выбранного окна. Пропуски требуют отдельного
разрешения и остаются в отчёте. Прогрев начинается на выбранной истории; достаточность
прогрева пользователь задаёт явно. При отдельном начале оценки состояние индикаторов
вычисляется на прогреве, а приказы до начала оценки не исполняются. Это работает
также без настраиваемых `input` (`run-plan.6.settings = null`).

Для v1/v2 historical lookahead on требует полный старший бар, пересекающий конец
основного диапазона; его финальное значение доступно с открытия. Для off запрашиваются
только закрытые к концу диапазона старшие бары. Предупреждение показано у контекста.
Модель остаётся реконструированной по закреплённым артефактам; сверка с TradingView
проводится отдельно.

Запуск создаёт одно задание с идентификатором подготовки. Повтор HTTP-запроса и
восстановление после сбоя между INSERT задания и сохранением ссылки не дублируют его.
Для нового расчёта после завершения создаётся новая подготовка. Пауза и продолжение
используют совместный checkpoint существующего worker. После перезагрузки страницы
восстанавливаются программа, параметры, источники, окно, подготовка и её задание.
Остановленную подготовку можно продолжить; отмена не прерывает общую загрузку истории
других потребителей. Готовые подготовки являются корнями GC и резервной копии.

Experiment/search/walk-forward получают тот же подготовленный граф ссылок.
Собственные окна selection/holdout/walk-forward задаются в формах исследований;
они не наследуют интервал оценки обычного запуска. В результатах доступен сохранённый
исходник и параметры; «Открыть копию» переносит их в редактор, «Повторить» создаёт
новый расчёт на тех же снимках. Старые IR без сохранённого исходника доступны в API,
но открыть исходник в редакторе для них невозможно.

## HTTP

- `POST /api/launches` — `openpine.launch-request.1`: request_id, input_ref,
  primary, contexts, inputs, timeout_seconds, gap_policy; опционально window,
  broker_settings, checkpoint_interval_bars, pause_after_bars.
- Источник: `{kind:"snapshot",snapshot_id}` или `{kind:"history",request:HistoryRequest}`.
- `GET /api/launches/{id}` — durable status, config и готовый prepared/base.
- `POST /api/launches/{id}/start|cancel|resume` — пустой объект.
- `GET /api/launches/requirements?input_ref=...`, `/api/launches/{id}/source|sources`.
- `GET /api/launches/snapshots?offset=0&limit=50` — каталог без чтения всех свечей.
- `POST /api/launches/history-spec` — предложение диапазона дополнительного контекста.
- `GET /api/jobs/{id}/configuration` — исходник, параметры, закреплённые request/plan,
  идентичности данных и текущее состояние задания.

До семи дополнительных контекстов, 64 input, таймаут до 3600 секунд.
Веб-загрузка отдельного файла контекста ограничена 8 МиБ; большие данные выбираются
из каталога или загружаются провайдером. Все изменяющие HTTP-маршруты используют
существующий локальный токен. CLI `openpine job --contexts ...` сохраняется как
независимый путь сравнения результата с серверной подготовкой.

Приёмка: [план](LAUNCH_PLAN.md). Нагрузочный сценарий:
`python -m tools.launch_soak --directory NEW_DIRECTORY --bars 1000000`.
Он проверяет полный worker с Parquet и старшим контекстом, продолжение после
перезапуска координатора, реальное падение worker и восстановление из backup.

[Приёмка 24 октября 2026](evidence/launch-20261024.json) закрывает все семь пунктов:
495 тестов / 59 модулей, 623 conformance-сценария и девять успешных CI jobs.
Независимая проверка Parquet охватывает 3 млн выходных точек; сравнение после
падения worker и backup/restore выполнено на отдельных 100 тыс. свечей.
