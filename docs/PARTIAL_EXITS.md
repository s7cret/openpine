# Частичные исполнения исторических стратегий

Выпуск `pine-partial-exits-20261024.1` закрепляет отдельные профили
`openpine.partial-exits.vN.1` для v1–v6. Артефакты v4–v6 явно содержат qty
и qty_percent у close/exit; v3 содержит их у exit. Недостающие ранние
сигнатуры восстановлены явно и отмечены в review и compatibility notes.
Результаты внешнего исполнения TradingView не использовались.

```pine
//@version=6
strategy("Partial exits",default_qty_type=strategy.fixed,initial_capital=1000)
if bar_index==0
    strategy.entry("L",strategy.long,qty=10)
    strategy.exit("first","L",stop=95,limit=110,qty=5)
    strategy.exit("rest","L",stop=95,limit=120,qty_percent=100)
plot(strategy.position_size)
plot(strategy.equity)
```

Именованный qty/qty_percent у exit или close выбирает
`openpine.partial-broker.1` для всей программы. Остальные команды этой
программы могут использовать прежние формы. Программы без явного нового
параметра сохраняют market/protective broker .1 и его поведение.
`strategy.close("L",qty=5)` закрывает часть market-заявкой со следующего open.

## Количество и резервирование

Определённый qty имеет приоритет над qty_percent; неактивный процент не
определяет количество. Qty — неотрицательное число. При qty=na используется
процент, а при неопределённом проценте — 100%. Процент ограничен 0…100.
Количество округляется вниз до quantity_step и ограничивается доступным
остатком. Нулевой результат не создаёт исполнения и записывается в журнал.

До 16 bracket-групп с разными exit ID резервируют объём в порядке команд.
Процент рассчитывается от текущего количества выбранного входа, после чего
запрашиваемый объём ограничивается ещё не зарезервированной частью.
Например, две заявки по 50% входа на 10 единиц получают по 5. Вторая заявка
на 100% после первой на 5 также получает оставшиеся 5.

Изменение exit ID освобождает его старую бронь и создаёт новую заявку,
доступную со следующего бара. Отмена освобождает бронь. Другим выходам
освободившийся объём автоматически не добавляется. Ручное закрытие уменьшает
существующие брони в порядке их создания; нулевая бронь отменяется.
Цена и количество связываются с точным fill либо ожидающим entry order.
Новый ожидающий разворот с тем же ID может получить защиту нового направления.
Старые группы отменяются при закрытии старой позиции и не переходят к
позднему несвязанному входу с тем же текстовым ID.

## Исполнения и деньги

Market-команды исполняются на следующем имеющемся open. Количество close
фиксируется при создании команды, связывается с исходным fill и при исполнении
ограничивается остатком. После более раннего разворота устаревший close
игнорируется; новую позицию он не закрывает.

Затем исполняются известные пересечения защитных уровней на open. Для
неизвестного внутрисвечного порядка сначала проверяются stop-касания, затем
limit-касания; внутри категории используется sequence. При двойном касании
своей bracket выбирается stop и отмечается ambiguous. Это явное правило
модели, а не восстановление пути тиков. Stop/market получают adverse slippage,
limit — улучшение цены на благоприятном гэпе без slippage.

Каждый выходной fill создаёт отдельную закрытую часть trade с quantity,
remaining_quantity, gross_profit, net_profit, входной и выходной комиссией.
Счётчик trades/research closed_trades считает эти части; closed_positions
показывает количество полностью закрытых входов.

Входная комиссия распределяется по округлённой накопленной доле закрытого
количества; последняя часть получает точный остаток. Комиссия каждого fill
округляется по money_decimals. Расчёт principal и PnL ведётся в Decimal с
точностью 80 знаков. Обычные денежные итоги округляются для отображения;
cash_exact/equity_exact/gross_realized_exact/unrealized_exact сохраняют
аудируемые значения. Для них выполняется тождество:

`cash_exact = initial_capital + gross_realized_exact - commission - open_principal`.

Сумма входной и выходной комиссии равна общей commission; нераспределённая
входная комиссия равна комиссии оставшейся позиции. Входная цена при
частичном закрытии не меняется.

## Восстановление и приложение

`openpine.broker-state.3` сохраняет исходное и оставшееся количество, долю
комиссии, счётчики частей, точные targets, ожидающие команды и брони.
Закрытый reader проверяет типы, диапазоны, идентичности, шаг количества,
денежные тождества и сумму резервов до присваивания состояния. Состояния .1/.2
не мигрируют в новый профиль автоматически. Ошибка begin/commit закрывает
чистый broker для дальнейшего исполнения и публикации checkpoint.

`openpine.simulation.3` и `openpine.chart-window.3` передают список защитных
выходов. Журнал остаётся в Parquet; SQLite содержит небольшие метаданные.
График получает только выбранный диапазон и начальный mark; лимит событий
5000 и признак truncated сохраняются. В таблице видны количество исполнения,
остаток, комиссия и результат закрытой части.

Повторный исторический запуск из сохранённых IR/снимков и продолжение после
backup используют тот же broker. Observed/live replay сохраняет явный
`PROTECTION_CONFIRMED_ONLY`: исполнения по обновлениям незакрытой свечи
не входят в этот исторический профиль.

## Примеры и приёмка

Шесть [примеров](../examples/partial-exits/) используют параметр First take,
90 собственных синтетических циклов и два выхода. По умолчанию каждый цикл
при входе 10 по 100 закрывает 5 по 110 и 5 по 95. При комиссии 1%:
gross=25, commission=20.25, net=4.75; 90 циклов дают equity=1427.5.
С First take=4 каждый цикл даёт net=-10.1 и итоговую equity=91.

Новый [корпус](../conformance/partial-exits/cases.json) содержит 54 исполнения
и 30 ожидаемых отказов. Ожидания заданы независимо, без запуска broker.
Шесть прежних `vN-reject-qty` в exits сохранены с исходными текстами и теперь
проверяют допустимую команду без подходящего входа: нулевые fills, orders и PnL.
Их прежний UNKNOWN_ARGUMENT снят намеренно; остальные старые наблюдения сохраняются.
Полная приёмка: [план](PARTIAL_EXITS_PLAN.md).

За границей выпуска: pyramiding, stop/limit-входы, trailing, profit/loss,
произвольные OCA-группы и наблюдаемое защитное исполнение. Имена ID остаются
литеральными; when допускается только в v1–v5. Эти ограничения проверяются
статически либо явной диагностикой исполнения.
