# Исторические стратегии R6

Первый замкнутый бэктест: Pine → типизированный IR → общий исторический драйвер
→ заявки → исполнения → позиции/сделки/капитал → Parquet → CLI/HTTP.
Используются Python 3.14.8, прежние SQLite/DuckDB и неизменяемые снимки.

## Принятый объём и версии

Профили `openpine.strategy.v1.1` … `v6.1` закреплены отдельным неизменяемым
выпуском `pine-strategies-20261021.1`. Evidence ссылается на записи локальных
каталогов wiki и их SHA. Предыдущие bundles остаются неизменными.

| Версия | Направление entry | Условие when | Доказательства |
| --- | --- | --- | --- |
| v1 | `long=true/false`, без strategy.long/short | Принято нашей реконструкцией | Словарь имён без полных сигнатур |
| v2 | `long`, bool или strategy.long/short | Принято нашей реконструкцией | Имена и отдельные примеры |
| v3–v4 | `long`, bool или strategy.long/short | Поддерживается | Версионные сигнатуры артефактов |
| v5 | `direction=strategy.long/short` | Поддерживается по локальной записи параметров | Версионный каталог |
| v6 | `direction=strategy.long/short` | Отсутствует | Версионный каталог |

Это ограниченная модель по артефактам. Точное соответствие TradingView ещё не
проверялось. Для v1/v2 реконструкция отражена в compatibility notes.
Условия можно выражать обычными `if` во всех версиях.

Поддержаны `strategy`, `strategy.entry`, `strategy.close`,
`strategy.position_size`, `strategy.position_avg_price`, `strategy.equity`.
Можно читать историю торговых переменных через `[]` и использовать уже
реализованные индикаторы, функции, переменные и исторические запросы контекстов.

Обязателен профиль фиксированного количества: `default_qty_type=strategy.fixed`.
В v6 его нужно указать явно: родной default этой версии выходит за текущий срез.
Пример с явно закреплёнными начальными условиями:

```pine
//@version=6
strategy("Example", default_qty_type=strategy.fixed, default_qty_value=1,
         initial_capital=1000, commission_type=strategy.commission.percent,
         commission_value=1, slippage=0, pyramiding=0)
fast = ta.sma(close, 1)
slow = ta.ema(close, 2)
if ta.crossover(fast, slow)
    strategy.entry("L", strategy.long)
if ta.crossunder(fast, slow)
    strategy.close("L")
plot(strategy.equity, title="Equity")
```

В header позиционно принимается только title; остальные поддержанные параметры
требуют имён. У entry позиционны id/direction/qty, у close — только id. Таким
образом пропущенные limit/stop/comment не меняют смысл позиционных аргументов.
ID — непустая строка-литерал до 128 символов. Header требует литералы; qty может
быть вычисляемым числом, а `na` выбирает закреплённое default_qty_value.
Заявки разрешены как инструкции в глобальном/if-блоке, до 16 достигнутых команд
на бар и 64 написанных мест вызова. Стратегия может не содержать plot.

Default initial_capital: v5 — 1000000, v6 — 100000 по локальному каталогу;
v1–v4 — реконструированные 100000. Количество по умолчанию 1, комиссия 0%,
проскальзывание 0. Для сопоставимых экспериментов задавайте их явно.

## Порядок событий и брокер

1. Перед расчётом очередного primary-бара исполняются заявки предыдущего бара
   по его open, в стабильном порядке команд. Заявка никогда не исполняется на
   баре создания. Пропуск времени переносит её на следующий имеющийся бар.
2. Контексты обновляются по прежним правилам доступности. Программа вычисляется
   один раз на подтверждённом close. Виден результат исполнений текущего open,
   а equity оценивается по текущему close.
3. Успешный расчёт создаёт заявки на следующий бар и фиксирует mark капитала.
   Только после этого можно публиковать checkpoint. Ошибка внутри бара
   исключает публикацию его частичного результата.

Одна открытая запись позиции; pyramiding=0. Entry в ту же сторону игнорируется
при исполнении, противоположный entry закрывает всю позицию и открывает новую
заданного размера. Это два fill, каждый со своей комиссией. Close закрывает
только позицию с совпадающим entry ID, иначе записывает причину игнорирования.
Повторные команды одного ID на одном баре заменяют предыдущую ожидающую команду,
сохраняя её место в очереди. Разные ID обрабатываются в порядке инструкций.
Последний бар оставляет открытые позиции и ожидающие заявки; искусственной
ликвидации в конце данных нет.

`simulation` — чистый модуль: зависит только от contracts, не обращается к
SQLite, файлам, HTTP или процессам. Драйвер передаёт цены/команды и сохраняет
события через порт вывода. Runtime читает предоставленные позиции и создаёт
типизированные intents; он не управляет брокером и хранением.

## Деньги, количество и инструмент

Линейный инструмент в валюте котировки, multiplier=1. Cash изменяется на
подписанную стоимость сделки и комиссию; equity = cash + position × close.
Gross realized суммирует результат закрытых позиций; trade net включает
комиссии входа и выхода. Остаток позиции и unrealized публикуются отдельно.
Начальный капитал — условие учёта; этот профиль не проверяет обеспечение и
не моделирует маржу, ликвидацию, FX, дивиденды или funding.

Арифметика Decimal с precision 80. Числа Pine сначала имеют свою принятую
float-семантику, затем переводятся через их десятичное представление. Комиссия
округляется на каждом fill методом HALF_EVEN до money_decimals. Raw cash и
gross сохраняют точность, публикуемые деньги округляются до той же шкалы.
Журнал/статистика хранят десятичные строки; значения Pine/plot — float.

BrokerSettings по умолчанию: tick_size=null, quantity_step="0.00000001",
money_decimals=8. Это вычислительный профиль, а не правила выбранной биржи.
Количество строго положительно и кратно закреплённому шагу, без скрытого
округления. Все primary open/close должны быть определёнными положительными
ценами; close-only вход для стратегии отклоняется.

`slippage` — целое количество тиков в неблагоприятную сторону каждого fill.
Для ненулевого значения нужен явно заданный tick_size. Он не выводится из
OHLCV. Настройки можно передать файлом:

```json
{"schema_version":"openpine.broker-settings.1","tick_size":"0.5","quantity_step":"0.1","money_decimals":2}
```

## Запуск и результаты

```powershell
openpine job --source examples/strategies/v6.pine --bars examples/strategies/wave.json --state-dir .runtime/trading --pause-after 2
openpine job --resume JOB_ID --state-dir .runtime/trading
```

Для старшего таймфрейма используйте `v6-filtered.pine` и
`--contexts examples/strategies/inputs.json`. Примеры есть для всех v1–v6.
`--broker-settings FILE` закрепляет инструмент/округление нового запуска;
resume использует сохранённую политику и не принимает её подмену.

Прежние HTTP job-request .2/.3/.4 работают и со стратегиями. Новый .5 принимает
ровно input_ref/snapshot_id/timeout_seconds, primary_context (nullable), contexts,
broker_settings и schema_version; HTTP также допускает пару
checkpoint_interval_bars/pause_after_bars. `GET /api/jobs/ID/plan` показывает
фактически закреплённую политику. `GET /api/jobs/ID/ledger?start=0&limit=2000`
читает журнал по sequence, до 5000 событий на страницу, с next/total.
Marks содержат ряд капитала, fills — исполнения, trades — закрытые сделки.
`plot(strategy.equity)` доступен существующему окну графика без полной выгрузки.
ID торговых сущностей детерминированы программой и порядковым номером; при
объединении результатов разных запусков используйте пару result_id/entity_id.

RunPlan .4 содержит BrokerPolicy вместе со снимками, spec/implementation hashes
и ресурсами. Payload старых планов .1/.2/.3 сохраняется. Новые стратегические
summary .5 / малые run-result .4 дополняют прежние форматы. SQLite остаётся v3:
новые структуры размещены в имеющихся immutable plan/result/checkpoint roots.
Изменение вычислительного ядра/spec требует перекомпиляции старого IR.
При подготовке стратегии исходник сохраняется через source_ref, а компиляция —
через artifact_ref. Политика выводится из этого IR; worker получает тот же
артефакт. Координатор не загружает компилятор повторно при submit и не держит
отдельную compiler Session у каждого локального менеджера. Обычные исходники
индикаторов сохраняют прежнюю компиляцию в worker.

## Совместное восстановление и приёмка

Trading-state .1 объединяет runtime/context state с broker-state .1: pending
orders, позиция, cash/fees/realized, курсоры и детерминированные ID. Корневой
execution-checkpoint .1 по-прежнему связывает всё с хешем полного RunPlan.
Output-prefix .2 добавляет trade-prefix .1. Журнал пишется в блоки по 100000
событий в Parquet/ZSTD; незавершённый CSV-хвост закрепляется отдельным объектом.
Пауза не меняет физические границы блоков. Backup/restore/prune/GC обходят
ссылки на журнал в checkpoint и завершённом результате.

24 независимых conformance cases (18 исполнений, 6 отказов) покрывают v1–v6,
следующий open, комиссии, позиции, пересечения средних и старший контекст.
Дополнительно проверяются все границы малых программ, совместное восстановление
контекстов/брокера, short/reverse, реальные падения worker/координатора,
сбой записи журнала, CLI/HTTP и установка wheel вне checkout.

```powershell
python -m tools.release_gate
python -m tools.install_check
python -m tools.strategy_benchmark --directory ../trading-proof --bars 1000000 --pause-after 123457
```

Локальная большая приёмка основного этапа (`41cf6e9`): 1000000 primary-баров и 250000 дополнительных,
2000000 значений plot в 20 блоках и 3499998 событий журнала в 35 блоках.
После паузы на 123457-м баре, backup/restore и нового процесса совпали вся
сводка и физические Parquet-файлы; баланс независимо пересчитан по входным ценам.
Runtime checkpoint — 2255 байт, один pending order, requested cursor 30864.
Непрерывный запуск — 149,819 с, продолжение — 134,742 с; пиковый наблюдённый RSS
около 128 MiB при лимите 512 MiB. Это измерение данного Windows-хоста и набора.
Сводка доказательств и установки: [evidence/strategies-20261021.json](evidence/strategies-20261021.json).

За пределами профиля: limit/stop, частичные закрытия, pyramiding, OCA, intrabar,
пересчёт на fill/тиках, process_orders_on_close и остальные API стратегии.
Неподдержанные параметры получают явную диагностику. Полное покрытие strategy
и совпадение с TradingView этим этапом не заявляются.
