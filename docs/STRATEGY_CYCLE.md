# Фазы расчёта стратегии

`openpine.strategy-cycle.1` разделяет ценовые наблюдения и проходы Pine.
Общий scheduler используется историческим driver и live/replay, с прежними
evaluator, брокером, lot ledger и портами хранения.

## Версии и выбор

| Параметр Pine | v1 | v2–v3 | v4–v6 |
| --- | --- | --- | --- |
| `calc_on_every_tick` | Не подтверждён | Да | Да |
| `calc_on_order_fills` | Не подтверждён | Да | Да |
| `process_orders_on_close` | Не подтверждён | Не подтверждён | Да |

Доступность имён взята из закреплённых reference-записей. Хеши и entry IDs
находятся в `spec/strategy-cycle-profile.json`. Это свидетельства параметров;
порядок фаз и ограничения ниже являются явным исполняемым контрактом OpenPine.
Эквивалентность TradingView проверяется отдельно.

Все параметры требуют const bool. Неподтверждённые source-параметры, в том числе
со значением false, отвергаются. Значения по умолчанию — false. Явная
конфигурация `cycle_settings` позволяет реконструкцию ранних версий v1–v6;
она не меняет допустимый синтаксис Pine. Конфликт с явно указанным параметром
исходника отвергается. `varip` сохраняет прежнюю границу v4–v6.

Использование одного из двух новых source-параметров выбирает новый профиль,
даже если параметр false. Прежние заголовки и профили сохраняют свой контракт.
`calc_on_every_tick` без новых параметров продолжает выбирать предыдущий
профиль расчёта на обновлениях.

## Порядок одного основного события

1. Общий брокер получает цену и исполняет ранее доступные заявки.
2. Если пачка дала исполнения и включён `calc_on_order_fills`, проходит
   `after_fill`. Pine видит обновлённые позицию, лоты и статистику.
3. Проходит `regular`: на close всегда, на open/update только при
   `calc_on_every_tick`. На close после `after_fill` это отдельный проход.
4. Если включён `process_orders_on_close` и событие — close, брокер делает
   одну дополнительную обработку активных заявок по известной цене закрытия.
   Старые cumulative high/low не становятся новым ценовым путём.
5. Если эта обработка дала исполнения и включён `calc_on_order_fills`,
   проходит `after_close_fill`.
6. Последний проход закрытой свечи фиксирует runtime, историю и plot один раз.

Пересчёт назначается после атомарной пачки брокера, а не после каждого лота
или фрагмента FIFO. Один reversal или пачка OCA/защиты могут содержать несколько
исполнений. Промежуточная позиция внутри такой пачки не видна скрипту.

Команды проходят прежние правила количества, комиссий, риска, OCA и trailing.
Pending-команды сохраняются между проходами; новые команды с тем же ID
заменяют прежние, явная отмена продолжает действовать. По умолчанию команда
доступна на следующем ценовом наблюдении. Дополнительная close-обработка —
единственное исключение: она может исполнить уже созданные к этому моменту
заявки. Команды из `after_close_fill` ждут следующей цены.

Повторной close-обработки или рекурсивного исполнения новой команды на той же
цене нет. Текущая схема даёт до трёх проходов на наблюдение; общий защитный
бюджет — 32, с диагностикой `CALCULATION_BUDGET`. Каждый проход сохраняет
прежние бюджеты работы, памяти, чтений истории сделок и 16 команд.

## Состояние, контексты и история

Обычные переменные, var, TA и история каждого прохода берутся с последнего
подтверждённого бара. Varip и доступные через него primitive arrays сохраняют
изменения между всеми основными проходами. На закрытии фиксируется последняя
ветка без повторного выполнения Pine. Изменённые ячейки окон применяются
через overlays; полная история для этого не копируется.

Дополнительные запросы рассчитываются только на собственных событиях.
Пересчёт основной стратегии после исполнения повторно использует уже известное
значение запроса, сохраняя availability, gaps и lookahead.

`observations`, `passes`, счётчики фаз и `(event_sequence, phase, ordinal)`
имеют разный смысл. Последние проходы показываются в статусе. Чтение статуса,
повтор события и восстановление не запускают Pine.

В историческом driver первоначальная пачка использует существующую явно
описанную OHLC-модель. После неё пересчёт видит известный полный бар;
дополнительная close-обработка использует только close. Искусственные тики
между OHLC не строятся. В observed/live используются только полученные цены.

## Публикация и восстановление

Один input event со всеми его фазами — единица атомарной публикации. Между
фазами worker может иметь непубликованные изменения. При сбое до commit они
отбрасываются, событие повторяется от последнего опубликованного рубежа.
После commit новый worker восстанавливает весь рубеж без повторных исполнений.
Промежуточная половина события не публикуется как готовая контрольная точка.

Новые формы: `openpine.replay-state.4`, `openpine.observed-cycle-state.1`,
`openpine.strategy-cycle-state.1`, исторический `openpine.trading-state.2`,
`openpine.replay-config.5`, запись `openpine.session-recording.4`.
Схема SQLite не меняется. Состояние включает счётчики фаз, последнюю идентичность
прохода, varip-корни, preview и собственные состояния запросов. Валидатор
проверяет их вместе с наблюдениями брокера и подтверждённым runtime.

## Запуск

```pine
//@version=6
strategy("Entry and protection", default_qty_type=strategy.fixed,
         calc_on_order_fills=true, process_orders_on_close=true)
if bar_index == 0 and strategy.position_size == 0
    strategy.entry("L", strategy.long)
if strategy.position_size > 0
    strategy.exit("X", "L", limit=110)
plot(strategy.position_size)
```

CLI с версионными примерами:

```sh
openpine replay create --source examples/strategy-cycle/v6-protection.pine --contexts examples/strategy-cycle/contexts-protection.json --calculation-profile cycle --calc-on-order-fills --process-orders-on-close
openpine replay append --id ID --events examples/strategy-cycle/events.ndjson
openpine replay advance --id ID --max-events 1 --checkpoint-every 1
openpine replay advance --id ID
```

HTTP replay/live принимает профиль и строгие bool-настройки:

```json
{"calculation_profile":"openpine.strategy-cycle.1","cycle_settings":{"calc_on_every_tick":false,"calc_on_order_fills":true,"process_orders_on_close":true}}
```

Веб предлагает два отдельных флажка и показывает фактические сохранённые
режимы, число проходов и причину последнего. После создания настройки
закреплены. Запись переносит настройки, preview, фазы и журнал для офлайн replay.

В `examples/strategy-cycle` — 27 собственных программ с явными ожиданиями,
включая реконструкции ранних версий, защиту, рыночное закрытие, var/varip,
массивы и ожидание следующей цены. [План приёмки](STRATEGY_CYCLE_PLAN.md).
