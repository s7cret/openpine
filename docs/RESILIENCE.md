# Устойчивые запросы и исследования

Изменения относятся к HTTP, каталогу, клиентам и приёмке. Семантика Pine,
компилятор, runtime и торговая модель сохраняются. Python для проверки — 3.14.8.

## Занятость координатора

`503 COORDINATOR_BUSY` содержит обычные `diagnostics` и дополнительный объект
`admission` версии `openpine.admission.1`: `kind`, `reason`, `active`,
`reserved_mb`, `retryable`, `retry_after_ms`. `reason` различает `slot_limit`,
`memory_reservation`, `resident_memory`, `reservation_upgrade` и `connections`.
Сервер также возвращает числовой `Retry-After` в секундах. Ограничение соединений
возвращает тот же JSON, а не пустой ответ.

Ограниченные операции над метаданными имеют два слота и используют уже
зарезервированный `base_mb`. Они не открывают IR, свечи, результаты или экспорт.
Повышение такой резервации до тяжёлого чтения/подготовки запрещено. Проверка
реальной памяти процесса сохраняется. Долгие тяжёлые HTTP-запросы используют
не более `max(1, connections-2)` соединений. При стандартных восьми соединениях
два остаются для коротких запросов. Общие блокировки каталога и атомарные
критические секции при этом не обходятся.

Полный статус исследования остаётся прежним. Дополнительные маршруты:

```text
GET /api/experiments/ID/progress
GET /api/searches/ID/progress
GET /api/walkforwards/ID/progress
```

Они возвращают `openpine.research-progress.1`: идентификатор, название,
желаемое/наблюдаемое состояние, счётчики и краткую ошибку. Для прежних POST
`pause/resume/cancel` заголовок `X-OpenPine-Control-View: progress` выбирает
такой же лёгкий ответ. Без заголовка сохраняется полный прежний ответ.
CLI и веб используют лёгкое представление; управление не перечитывает
большие результаты ради подтверждения команды.

## Политика повторов

CLI и веб ограничивают один HTTP-вызов восемью попытками и общим сроком 120 с.
Задержка растёт от 50 до 800 мс; числовой `Retry-After` учитывается с пределом
2 с на задержку. Повторяется занятое чтение или безопасное чтение после
транспортного сбоя. Смешанные диагностики, ошибки хранения, авторизации,
валидации и протокола не маскируются повтором `busy`.

POST автоматически повторяется только для трёх маршрутов создания исследований
с сохранённым ключом. Остальные POST, включая команды управления, не
переотправляются автоматически после неопределённого результата.
HTTP-коды, исходные диагностики и сведения о занятости сохраняются в выводе
CLI. При неопределённом ответе на создание также возвращаются ключ и путь
клиентского файла операции.

## Одно создание на ключ

Для `POST /api/experiments`, `/api/searches`, `/api/walkforwards` необязательный
заголовок `X-OpenPine-Request` содержит 32 строчных hex-символа. Без него
сохраняется прежний интерфейс создания. С ключом ответ — квитанция
`openpine.research-operation.1` с `request_id`, `request_sha256`, `resource_id`,
идентификатором соответствующего исследования и `status=accepted`.

Ключ принадлежит паре `(kind, request_id)`. Отпечаток вычисляется от canonical
JSON всего запроса, включая закреплённые программу, снимок и параметры.
Повтор возвращает ту же квитанцию; другой запрос с тем же ключом даёт
`409 IDEMPOTENCY_CONFLICT`. Перепроверка квитанции выполняется до тяжёлой
подготовки. Квитанция и вся композиция исследования сохраняются одной SQLite
транзакцией. Сбой между их публикациями откатывает обе части.

```text
GET /api/operations/experiment/REQUEST_ID
GET /api/operations/search/REQUEST_ID
GET /api/operations/walkforward/REQUEST_ID
```

Отсутствующая квитанция даёт `404 OPERATION_NOT_FOUND`. После предусмотренного
удаления исследования ключ остаётся зарезервированным и даёт
`410 OPERATION_GONE`. Маркер удаления и удаление ресурсов атомарны; отсутствие
ресурса без такого маркера считается нарушением целостности. Backup сохраняет
квитанции вместе с каталогом. SQLite schema 14 добавляет эту таблицу; прежние
данные schema 13 мигрируют без переписывания.

## Клиентская отправка

```sh
openpine search run --server http://127.0.0.1:8765 --request request.json --source strategy.pine --bars bars.json --operation-file search-operation.json --output result.json
```

Те же параметры доступны для `experiment` и `walkforward`. CLI сохраняет
ключ и закреплённое тело до отправки. Повтор команды с тем же намерением
восстанавливает прежнюю операцию, не компилирует заново её исходник и не
заменяет сохранённые ссылки. Файл операции имеет отдельную межпроцессную
блокировку, без открытия каталога/manager lock сервера.

Без `--operation-file` используется `OUTPUT.operation.json`, если задан
`--output`, иначе файл в `.runtime/client-operations`. `--request-id` задаёт
ключ явно. Для намеренно нового создания после принятой операции служит
`--new-request` либо другой файл операции. Неподтверждённую отправку нельзя
молча перезаписать изменёнными параметрами. После доказанного отказа без
квитанции параметры можно исправить. Файл операции не должен совпадать
с запросом, исходником, данными или выходным файлом.

Веб сохраняет неподтверждённую отправку в localStorage своего origin до ответа,
показывает ожидание ресурсов/повтор соединения и позволяет прекратить ожидание.
Это не отменяет уже принятую работу. Перезагрузка сначала проверяет квитанцию;
если её ещё нет, панель позволяет повторить отправку по тому же ключу.
Сохранённое тело ограничено 1 МиБ. Принятый идентификатор восстанавливается
в карточке исследования. Для переноса между другими адресами сервера
идентификаторы и файл операции используются явно; origin не подменяется.

## Приёмка и общий wheel

CI строит один переносимый wheel и source-bound manifest. Обе ОС и все
11 установочных групп используют SHA именно этого wheel. RECORD, исходные
файлы, метаданные, execution identity и полная build identity проверяются
до/после установки. Файлы `.gitkeep`, входящие в build identity, включены в
wheel; генерируемый каталог `conformance/results` в пакет не попадает.

`tools.release_gate` без дополнительных флагов остаётся полной локальной
проверкой. CI запускает `--section specification` один раз на каждой ОС,
а затем `--section tests --qualification ...` по трём шардам. У шардов
отдельные оценки длительности для Windows/Linux по принятому предыдущему CI.
Fast feedback и отдельный тестовый шард не являются полной приёмкой.

`tools.ci_artifacts accept` проверяет две спецификации, шесть шардов и
22 установочные квитанции: один source identity, один SHA wheel, точный набор
модулей и уникальных test IDs на каждой ОС, все установочные helpers и
результаты всех conformance-корпусов. Пропуски, дубли, другая сборка и
подменённые квитанции отклоняются. [План и результаты](RESILIENCE_PLAN.md).
