# Обновление и диагностика R6

Это текущая эксплуатационная точка входа. Документы отдельных этапов сохраняют
описание принятых тогда схем; их номера не являются текущей версией всего продукта.
Расчётные правила Pine v1–v6 этим этапом не изменены.

| Контракт | Текущая граница |
| --- | --- |
| Окружение приёмки | Python 3.14.8, SQLite 3.54.1, DuckDB 2.0.0.dev2610192346, Parquet/ZSTD |
| SQLite-каталог | **16**; миграция 16 добавляет неизменяемую связь нового задания с предшественником |
| Совместимость вычислений | `openpine.execution-identity.2`; compiler/contracts/runtime/simulation и участвующие в вычислении адаптеры |
| Происхождение сборки | `openpine.build-identity.1`; изменение UI/CLI само по себе не запрещает продолжение |
| Программа | `openpine.program-artifact.2`, чтение `.1` сохраняется; Typed IR определяется профилем, единого номера для всех срезов нет |
| План / запрос задания | Чтение прежних планов сохраняется; максимальные текущие схемы RunPlan `.7`, JobRequest `.8` |
| Checkpoint | `openpine.execution-checkpoint.1/.2`, records/tree envelopes; native-состояние не мигрирует между несовместимыми вычислениями |
| Обновление / диагностика | `openpine.upgrade.1`, `openpine.doctor.1`, `openpine.compatibility.1` |
| Новый запуск | `openpine.restart-preview.1`, `openpine.restart-receipt.1`; один новый job/plan/lineage commit |

## Проверка перед обновлением

Команды используют каталог заданий: для `serve --state-dir .runtime` это
`.runtime/jobs`. Параметр `--state-dir` обозначает папку с `catalog.sqlite3`.

```powershell
openpine doctor --state-dir .runtime/jobs
openpine doctor --full --state-dir .runtime/jobs
openpine compatibility --state-dir .runtime/jobs --kind jobs --start 0 --limit 50
openpine diagnostics --state-dir .runtime/jobs --output ../openpine-diagnostics.json
```

`doctor` не создаёт отсутствующее хранилище и не открывает исходный SQLite на
запись. Он читает временную копию catalog + WAL, проверяет стабильность файлов
до/после копирования и целостность копии. При изменении файлов делает до трёх
попыток. Если источник продолжает меняться, требуется повторить проверку.
Это наблюдение одного момента, а не гарантия дальнейшего отсутствия изменений.
Копия ограничена 512 МиБ; при превышении даётся явный отказ. Временная папка
проверяется на свободное место. Само обновление не ограничено этим размером копии.

Быстрый режим проверяет окружение, версии, quick_check, внешние ключи, наличие
владельца и количество записей. Полный выполняет integrity_check и обход известных
достижимых объектов с проверкой хешей, без публикации/удаления. Полный обход
ссылок доступен только для текущей схемы. Для старой/более новой схемы сначала
показывается требуемое действие. Повреждение не исправляется автоматически.
`storage inspect` тоже использует копию без миграций.

Отчёт совместимости постраничный, не более 100 записей. Группы: `jobs`,
`programs`, `replays`, `live`, `research`, `holdouts`, `launches`. Jobs включают
закреплённый план и манифест последнего checkpoint; research/holdouts — отдельные
неизменяемые варианты, включая ещё не отправленные в очередь. Live отдельно
проверяет преобразование данных и связанное воспроизведение. Replay сверяет
программу, execution identity и политику. Восстановление полного native-состояния
и проверка ресурсного допуска остаются обязанностью исполнения. Совпадение
идентичности не обещает наличие всех ресурсов или успешный будущий сетевой запрос.

## Управляемое обновление

Сначала поставьте нужные расчёты и исследования на паузу и дождитесь сохранения состояния, остановите live-сессии. Затем остановите сервер и дождитесь завершения оставшихся worker-процессов. Сначала
сохраните путь к предыдущему wheel/окружению: backup данных не содержит Python.

```powershell
openpine storage upgrade --state-dir .runtime/jobs --destination ../backup-before-r6-update
```

Команда получает `.manager.lock`, проверяет исторические и replay/batch attempt leases, сохраняет
`.upgrade.json`, создаёт проверенный backup **исходной схемы**, затем применяет
миграции и проверяет целостность и ссылки. Backup содержит все правильно
адресованные immutable objects, включая пока неиспользуемые; он не пытается
угадать корни неизвестной старой схемы. Это дополняет обычный backup достижимых
объектов. Исходная версия каталога и идентификатор операции закреплены отдельно.
Назначение backup должно быть новым и находиться вне хранилища.

После прерывания повторите **ту же команду той же сборкой**. Опубликованный backup
проверяется и используется повторно; незавершённая транзакция миграции откатывается
SQLite, уже завершённые миграции не повторяются. Изменение target identity,
подмена backup или его отсутствие после фиксации отклоняются. Пока receipt
не получил `complete`, обычный `Database` не допускает эксплуатацию этого каталога.
Сервер и обычные операции хранения также требуют явного обновления старой схемы.
Внутренний низкоуровневый `Database` сохраняет миграции для создания/тестирования;
точки входа приложения используют `require_current=True`.

Откат выполняется **в новую папку**, затем эта папка открывается предыдущей
установкой OpenPine. Исходное хранилище не перезаписывается:

```powershell
openpine storage restore --preserve-schema --source ../backup-before-r6-update --state-dir ../rollback-store
```

Без `--preserve-schema` остаётся прежняя семантика restore: привести копию к
схеме текущей установки. Хеши подтверждают целостность backup, не авторство.

## Несовместимое вычисление

Старые результаты доступны для чтения. Изменение execution/spec identity требует
нового запуска; старый RunPlan, checkpoint и live-журнал не переписываются.

```powershell
openpine restart JOB_ID --state-dir .runtime/jobs --output ../restart-preview.json
openpine restart JOB_ID --state-dir .runtime/jobs --preview-id PREVIEW_SHA --request-id UNIQUE_32_HEX
```

Предварительный отчёт перекомпилирует сохранённый исходник, сверяет inputs и
контексты с текущими контрактами, сохраняет ссылки на новые immutable артефакты,
но не запускает worker. Данные, окно исследования, magnifier и ресурсная политика
сохраняются; отличия нового плана перечислены в отчёте. Если input schema больше
не принимает прежние значения, требуется явная новая настройка через обычную
подготовку. Артефакт без сохранённого исходника автоматически не реконструируется.

Применение требует актуальный preview ID и request ID. Повтор с той же парой
возвращает прежнюю квитанцию. Job, RunPlan и неизменяемая lineage публикуются
одной транзакцией; старый результат остаётся на месте. Новый расчёт начинается
с бара 0. Offline-команда только ставит задание в очередь; выполнение начнётся
при обычном старте координатора. Ни preview, ни его offline-применение не запускают
другие сохранённые задания. Активный предшественник сначала ставится на паузу
или останавливается. Для research/live создаётся новая соответствующая композиция
через существующий интерфейс, а не скрытая замена старых планов.

## Веб и диагностический пакет

Карточка «Совместимость и диагностика» показывает причину, сохранённую точку и
доступное действие; результат можно открыть без перекомпиляции. Новый запуск
создаётся после просмотра отчёта отдельной кнопкой. Upgrade остаётся offline.
HTTP: `GET /api/maintenance/doctor`, `/compatibility`, `/diagnostics`,
`GET /api/jobs/ID/diagnosis`, `POST /api/jobs/ID/restart/preview` и `/apply`.
Пишущие операции сохраняют прежние проверки loopback/host/origin/token.

Экспорт диагностики по умолчанию ограничен 1 МиБ (CLI 4 КиБ–4 МиБ), содержит
только разрешённые поля: версии, хеши, идентификаторы, коды причин и сводки.
Исходники, настройки inputs, локальные пути, тексты ошибок, логи и свечи не
включаются. Пагинация/ограничение объёма явно отражаются флагом `truncated`.
Пакет скачивается пользователю; автоматической отправки третьим сторонам нет.

## Проверки

`test_upgrade.py` проверяет read-only WAL-копию, старую/новую/повреждённую схему,
leases, отказ backup, откат транзакции, реальные завершения процесса на пяти
границах и продолжение. Проверки replacement включают атомарность, повтор,
устаревший preview, сохранение результатов и отдельные решения replay/live/research.
`test_upgrade_http.py` проходит реальный HTTP → worker и проверяет токен/границы.
Installed helper `upgrade` включён в прежний suite `targets` на обеих ОС и исполняет переход двух сборок офлайн. Число CI jobs и suites не увеличивается.

`python -m tools.upgrade_acceptance --previous-wheel PATH --expected-sha256 SHA
--directory NEW` проверяет **две реальные установки**: предыдущий wheel создаёт
history/replay/research; текущая сборка обновляет каталог и продолжает их. Затем
в отдельной копии текущего wheel меняется вычислительный файл: продолжение
отклоняется, явная перекомпиляция создаёт новый расчёт с теми же свечами.
Производственный checkout при этом не меняется. Точная эквивалентность TradingView
остаётся отдельным этапом.

В `tests/fixtures/upgrade/` закреплён архив production-файлов предыдущего
принятого wheel: все `packages/`, `apps/`, `spec/`, параметры дистрибутива,
лицензия и четыре fixture-модуля с демонстрационными данными. Исходный wheel,
коммит, каждый член архива, build identity и execution identity записаны в
`baseline.json`. Архив около 1,8 МиБ не содержит зависимостей или исполняемых
бинарников. Это тестовый baseline, не второй runtime продукта.

`tools.upgrade_baseline` воспроизводит его из проверенного wheel/CI manifest
в новую папку. Замена baseline проходит обычный просмотр diff; новые файлы
не подменяются из сети во время теста. Installed helper использует
`tools.upgrade_acceptance --previous-fixture tests/fixtures/upgrade/baseline.json`.
Он проверяет точную identity предыдущего production-дерева перед созданием
состояния. Полный предыдущий wheel остаётся дополнительным локальным путём
проверки через `--previous-wheel` и закреплённый SHA256.
