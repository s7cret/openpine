# Стабилизация архитектуры R6

[Текущая эксплуатация R6: схема 16, диагностика и управляемое обновление](OPERATIONS.md). Ниже сохранено описание соответствующего исторического этапа.

Расширения основы: [несколько контекстов и RunPlan .3](CONTEXTS.md), затем
[торговый симулятор, RunPlan .4 и совместное восстановление брокера](STRATEGIES.md).

Следующий этап: [исторический драйвер и checkpoints](CHECKPOINTS.md).
Он расширяет описанную здесь основу: новые RunPlan имеют схему .2,
каталог — версию 4 после добавления [replay](REALTIME.md); исторические
checkpoints миграции 3 и прежний payload RunPlan .1 сохраняются.

Этап сохраняет существующий срез Pine v1–v6. Компилятор и runtime не получают
новых языковых возможностей. Python для приёмки — 3.14.8, SQLite — 3.54.1,
DuckDB — закреплённая 2.0.0.dev2610192346, файлы рядов — Parquet/ZSTD.

## 1. Совместимость и происхождение

`openpine.execution-identity.2` хеширует compiler/contracts/runtime, драйвер
Session, алгоритм идентичности, Python и jsonschema. Изменения HTTP, CLI,
оформления, процессов и SQL-адаптеров не меняют идентичность вычислительной
программы. Допуск IR и проверки spec/profile продолжают выполняться полностью.

`openpine.build-identity.1` отдельно хеширует все файлы packages/apps, включая
статические ресурсы, pyproject, spec lock, Python и зависимости хранения.
Это provenance сборки, а не основание для отказа исполнить совместимый IR.
Новый экспорт — `openpine.program-artifact.2`; внутри остаётся Typed IR 5.
Импорт принимает также прежнюю оболочку `.1`, но её старый общий хеш реализации
несовместим с новой схемой: такие программы нужно один раз перекомпилировать.
Сохранённые результаты и снимки не пересчитываются. Контрольные суммы не
удостоверяют автора артефакта.

## 2. Неизменяемый RunPlan

`openpine.run-plan.1` хранится в SQLite рядом с заданием и публикуется с ним
одной транзакцией. Поля: input_ref, snapshot_id, профиль исполнения, timeout,
потоки и память одной попытки, максимальное число попыток, heartbeat timeout,
схема результата, хеш вычислительной реализации и spec lock. Эти два хеша
проверяются также для исходного текста до компиляции: изменение реализации
после перезапуска даёт PLAN_IMPLEMENTATION, а не скрытую смену семантики.
Политика host concurrency/суммарного пула принадлежит
координатору, а настройки самого задания после приёма не изменяются.

Контрольная сумма плана проверяется при чтении и публикации результата;
UPDATE запрещён триггером. Worker получает тот же план. Изменение defaults
при перезапуске не меняет политику уже принятого задания. Если новый host не
может выделить закреплённую память/потоки, задание получает явный
`RESOURCE_POLICY_INCOMPATIBLE`; бюджет молча не уменьшается.

Каталог версии 1 транзакционно мигрирует в версию 2. Старым заданиям, где
настройки не сохранялись, план однократно присваивается из defaults первого
запуска новой версии. Восстановить неизвестную историческую политику невозможно.
Далее план сохраняется в backup и переживает перезапуски.
Компактный transport `job-request.2` сохранён. `GET /api/jobs/ID/plan` выдаёт план.

## 3. Сборка приложения и границы

`apps/openpine/bootstrap.py` собирает конкретные Database, ObjectStore,
CandleStore и JobRepository. `packages/execution` получает готовые зависимости:

- `Preparation` нормализует входы, сохраняет ссылки и выполняет политику импорта.
- `JobManager` управляет очередью, попытками и subprocess, fencing/heartbeat.
- `ResultReader` формирует сводки, окна и прежний ограниченный JSON-экспорт.
- `WorkLimiter` допускает подготовку/чтение по бюджету координатора.

Storage не импортирует execution, execution не импортирует storage/apps.
Compiler и runtime зависят от contracts и собственных модулей.
Проверка `python -m tools.verify_architecture` анализирует также вложенные и
относительные импорты. Она включена в release_gate и CI.

## 4. Допуск работы и повторное чтение

По умолчанию worker pool имеет бюджет 1024 MiB, координатор дополнительно
512 MiB (`--coordinator-memory-mb`). Итого бюджет приложения — 1536 MiB.
В координаторе резервируются 128 MiB базы, 256 MiB на подготовку и 128 MiB на
чтение. Одновременно допускаются максимум одна подготовка и два чтения,
дополнительно проверяется сумма резервов: одна подготовка оставляет место
только одному чтению. Вложенный вызов использует уже занятую резервацию.

HTTP ограничен восемью обслуживаемыми соединениями. Тяжёлая работа при
исчерпанном бюджете получает 503/COORDINATOR_BUSY, лишнее соединение — 503 с
Retry-After. Чтение тела тяжёлого POST начинается после допуска; состояние,
отмена и конфигурация остаются доступны без ожидания длинной подготовки.
Завершение сервера сначала дожидается обслуживаемых HTTP handlers.

RSS координатора проверяется перед допуском; supervisor учитывает RSS хозяина
и воркеров в суммарном лимите. Это admission и sampled RSS, не жёсткая
ОС-песочница: кратковременный скачок внутри уже выполняющейся операции возможен.
Полный JSON результата ограничен и 100000 барами, и 100000 значениями всех
выходных рядов вместе. Более крупные результаты выдаются сводкой и блоками.

Повторная выборка диапазона использует `selection_cache`: ключ включает
источник, точный запрос и упорядоченные ревизии покрытия. Повторное открытие
того же диапазона проверяет манифест без прохода по свечам. Новая ревизия,
включая пустую, меняет ключ; прежние снимки остаются неизменяемыми.

## 5. Квоты и обслуживание

Все принятые задания, зарегистрированные снимки и покрытие — корни хранения.
Компиляция/подготовленный вход дополнительно закрепляются pin, поэтому
сохранённый input_ref защищён даже до отправки задания. Backup фиксирует
SQLite и копирует только достижимые объекты этого снимка каталога; временные
и оставшиеся без ссылки результаты попыток в backup не попадают.

Команды по умолчанию только показывают результат. Администрирование берёт
тот же .manager.lock: сервер должен быть остановлен. Применение обслуживания
отклоняется, если в каталоге есть queued/running задания; сначала требуется
их восстановить/завершить/отменить.

```sh
openpine storage inspect
openpine storage quota --max-mb 20480
openpine storage gc
openpine storage gc --grace-seconds 3600 --apply
openpine storage prune --before 1792454400
openpine storage prune --before 1792454400 --expire-inputs --expire-coverage --apply
openpine storage gc --apply
```

`prune` удаляет старые terminal-задания и, при явных флагах, pins и покрытие.
Снимки удаляются из каталога только если на них не ссылаются оставшиеся задания
и покрытие. `gc` удаляет исключительно недостижимые объекты старше grace;
каталоги попыток очищаются лишь после явного удаления их задания.
Повреждение любого корня прерывает обслуживание до удаления файлов.

Квота относится к сумме опубликованных immutable objects. Она хранится в
SQLite, передаётся воркерам и проверяется под межпроцессной блокировкой записи.
Дедупликация не расходует квоту повторно. Ноль означает отсутствие квоты.
SQLite, логи, временные CSV/Parquet и резервные копии в эту квоту не входят;
резерв свободного места на файловой системе остаётся отдельным ограничением.
Автоматического удаления пользовательской истории при переполнении нет.

## 6. Приёмка

`tests/test_hardening.py` дополняет прежний gate сценариями совместимости
сохранённого IR при изменении HTTP, неизменности плана и повторов после
перезапуска, миграции каталога v1, повторного диапазона без чтения свечей,
конкурентного HTTP и резерва памяти, квоты в двух настоящих процессах,
защиты корней/активных заданий, preview/prune/gc и backup без orphan-объектов.
Проверка установленного wheel включает новый plan API, preview GC и сохранение
квоты. Большой прогон остаётся отдельной приёмкой на 100k/1m/10m свечей.

## Замеры 2026-10-21

Windows, Python 3.14.8, синтетические OHLCV и `plot(close)`. На 100k свечей
работали два настоящих процесса одновременно, на больших наборах — один.
Времена относятся к этому компьютеру; часть проверок шла параллельно.

| Свечей | Исполнение, s | Первый манифест диапазона, s | Повторный манифест, ms | Пик RSS worker, MiB |
|---:|---:|---:|---:|---:|
| 100000 | 4.225 | 0.2423 | 2.1 | 108 |
| 1000000 | 16.090 | 2.0844 | 2.9 | 105 |
| 10000000 | 131.515 | 19.6483 | 2.1 | 119 |

Повторный манифест не читает свечи, но проверяет свою неизменяемую JSON-запись.
Это отдельная операция от выдачи графика: последние 2000 точек на 10m выданы за
0.061 s. Запрос задания остался 233 bytes, больших массивов в нём нет.
Backup + restore + проверка большого результата заняли 3.031 s.

На отдельной копии реального каталога предыдущего этапа v1 проверены миграция
в v2, чтение прежнего сохранённого результата на 100k свечей и новый запуск:
ряды, число наблюдений и идентичность данных совпали. Исходный каталог не менялся.

Финальный gate: **213 тестов и 369 conformance-проверок**, Python 3.14.8.
Чистая установка вне checkout, CLI/HTTP, RunPlan, квота и backup/replay прошли.
[Машинный отчёт приёмки](evidence/stabilization-20261021.json) содержит хеши
вычислительной реализации, сборок и фактические измерения.
