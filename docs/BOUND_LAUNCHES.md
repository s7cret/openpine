# От паспорта к проверенному запуску

Прикладной слой связывает существующие программу, конфигурацию подготовки, снимки,
RunPlan и опубликованный результат. Нового binder, брокера или формата checkpoint нет.
Каталог сохраняет схему 16; расчётные правила Pine определяют прежние модули.

## Выбранные настройки

Описательный паспорт сохраняет шесть сравнительных вариантов. Опциональная
`selection` проверяет конкретный `execution_mode`: `history`, `replay` или
`magnifier`. Для replay принимаются существующие `event_profile`, `broker_profile`,
`calculation_profile`, `cycle_settings`, `environments`, `lower_tf` и настройки
брокера. Сочетания проверяет настоящий ReplayEngine. Неиспользованные параметры
перечисляются явно; replay-параметры в выбранном историческом режиме отклоняются.
Обычная история использует флаги программы; внешние исторические флаги фаз доступны
в существующей конфигурации Magnifier.

Веб передаёт настройки выбранного режима, включая переключатели наблюдения и
Magnifier. Подготовка исторического запуска возвращает просмотр в исторический
режим. Изменение программы, inputs, снимков, диапазона, настроек или выбранной
подготовки сбрасывает прежнюю проверку. Поздний ответ не подтверждает новый выбор.

## Закреплённая подготовка

`openpine.launch-binding.1` содержит идентичность подготовки, хеш конфигурации,
prepared object, запроса, плана, ссылки на вход и снимки, execution/spec identity.
`sha256` вычисляется по остальным полям. Он стабилен между повторными проверками
одной подготовки и меняется при другой конфигурации или подготовке.

`GET /api/launches/<id>/passport` сохраняет прежнее чтение без продвижения состояния
и добавляет `binding`. Для фактической проверки используется:

```text
POST /api/launches/<id>/validate
{"binding_sha256":"<sha256 выбранной подготовки>"}
```

Поле необязательно для совместимых клиентов; веб передаёт его явно. Действие
использует бюджет подготовки, не получает автоматических повторов и не создаёт
заданий или сетевых загрузок. Оно проверяет:

- соответствие конфигурации, frozen request, inputs и RunPlan;
- полные логические потоки свечей, количество строк и хеши Parquet-объектов;
- существующие правила покрытия и выбранную политику пропусков;
- метаданные инструмента через прежний reference reader в соответствующем контексте;
- конструктор того же streaming driver, который использует worker;
- покрытие Magnifier, OHLCV и допустимость видимости запрошенных свечей.

Pine по свечам не исполняется. Проверка читает потоки без сборки всей истории в RAM.
Бюджет потокового сканирования — 120 секунд с проверкой между пакетами чтения;
при превышении возвращается явный отказ. Он не прерывает уже начавшийся системный
вызов чтения. Диагностика указывает фазу: binding, целостность, покрытие,
метаданные инструмента, допуск драйвера или младшие свечи.
`openpine.launch-validation.1` указывает время, область проверки, строки/покрытие,
binding и checksum отчёта. Checksum не является отдельным адресом объекта каталога.
Отчёт можно сохранить через CLI или скачать в вебе; конфигурация и план уже
сохранены существующим механизмом подготовки.

`inputs_validated` означает проверенные входы данного момента. Свободная RAM,
диск и worker проверяются supervisor при допуске задания; ресурсы здесь не
резервируются. Перед первой постановкой в очередь `start` повторяет проверку
входов. Его тело допускает тот же `binding_sha256`. Повторный start уже созданного
задания сохраняет идемпотентность и не создаёт второе задание.

## Исполнение и записанные события

`GET /api/launches/<id>/execution` возвращает паспорт с
`openpine.launch-execution.1`. Он не опрашивает worker с продвижением состояния.
Положительное свидетельство требует `succeeded`, того же запроса/плана, совпадения
программы и снимка, полного числа баров, доступного committed result и читаемых
рядов/журнала. Только тогда `whole_program_execution_verified` становится `true`:
это свидетельство данного сохранённого запуска. Очередь, пауза, ошибка, таймаут,
отмена и повреждённый результат показываются отдельно.

`GET /api/replays/<id>/passport` описывает закреплённую конфигурацию и сохранённый
префикс исполнения. `POST /api/replays/<id>/validate` принимает необязательный
`binding_sha256` и проверяет байты, последовательности и цепочку accepted tape.
Используются существующие reader, ReplayEngine admission и checkpoint envelope;
события не применяются. При изменении ленты/публикации во время чтения проверка
отклоняется и требует повтора. Работающее наблюдение можно остановить обычным
управлением, чтобы проверить устойчивую запись.

Проверка ленты не доказывает допустимость всех переходов событий: её проверяет
движок при исполнении. Записанный префикс replay отделён от завершённого
исторического задания; `whole_program_execution_verified` для него остаётся `false`.

## CLI

Остановите сервер, владеющий этим каталогом. CLI использует существующую lease,
текущую схему и `autostart=False`; он не запускает сохранённые задания, не создаёт
отсутствующий каталог и не выполняет автоматическую миграцию старой схемы.

```console
openpine launch-passport --state-dir .runtime/jobs --launch-id <id>
openpine launch-passport --state-dir .runtime/jobs --launch-id <id> --check --binding-sha256 <sha256> --output ../checked.json
openpine launch-passport --state-dir .runtime/jobs --launch-id <id> --execution
openpine launch-passport --state-dir .runtime/jobs --replay-id <id> --check
```

Выходной файл должен находиться вне каталога. Код 2 означает отказ чтения/проверки.
CLI и HTTP используют одни функции; timestamps и checksum новой проверки могут
отличаться, устойчивый binding и сохранённый результат остаются теми же.

## Приёмка

Прежние 56 программ и 356 сравнений сохраняются. Пять существующих installed
частей дополнительно проводят 50 программ через настоящую подготовку, проверку
входов, worker и квитанцию. Семантический хеш результата сравнивается с прежним
путём; шесть ожидаемых отказов остаются отказами. Проверяются и существующие replay
ленты этих программ. Новые свидетельства публикуются отдельно от прежнего корпуса.
Офлайн CLI проходит v1–v6 после освобождения владельцем каталога; новых CI jobs нет.
Точное соответствие TradingView остаётся отдельным этапом.
