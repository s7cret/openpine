# Исторический драйвер и восстановление R6

Один `HistoricalDriver` управляет порядком баров для Session в памяти,
потокового исполнения и worker. Поддержаны имеющиеся конструкции Pine v1–v6.
Этот этап закрепляет нашу модель по локальной спецификации; сравнение с
TradingView остаётся отдельной приёмкой.

## Граница фиксации

Цикл: получить бар → исполнить все statements → зафиксировать history →
передать выходы бара sink → увеличить cursor. Выходы `plot` буферизуются до
успешного завершения statements. Ошибка вычисления не передаёт часть выходов
бара; ошибка sink делает evaluation непригодным для дальнейшего исполнения.
Незавершённую evaluation нельзя сохранить или опубликовать результатом.

Checkpoint возможен только после целого исторического бара. Публикация:

1. Неизменяемый объект runtime state.
2. Неизменяемый объект префикса выходов и его файлов.
3. Неизменяемый манифест с их хешами, программой, планом и снимком.
4. Атомарная ссылка `checkpoint.json` своей попытки.
5. Транзакция SQLite с проверкой действующей попытки и монотонности cursor.

Если процесс погиб между шагами, остаётся предыдущий целый checkpoint либо
новая целая ссылка, которую подхватит координатор при перезапуске. Объекты
без опубликованной ссылки убираются обычным явным GC. Старая/приостановленная
попытка не может заменить корень. Итоговый результат по-прежнему публикуется
отдельно после окончания всего входа; checkpoint не выдаётся за результат.

## Контракты состояния

| Запись | Схема | Содержимое |
| --- | --- | --- |
| Runtime | `openpine.runtime-state.1` | Хеш программы, cursor, context/time, `var`, history rings, состояния вызовов, бюджет и метаданные выходов |
| Выходы | `openpine.output-prefix.1` | Готовые Parquet-блоки, статистика рядов и незаконченный CSV-хвост |
| Корень | `openpine.execution-checkpoint.1` | Хеш RunPlan, snapshot/dataset, скомпилированный IR и ссылки на runtime/выходы |
| План | `openpine.run-plan.2` | Прежние неизменяемые поля и `checkpoint_interval_bars` |
| Каталог | SQLite `user_version=3` | Таблица последнего checkpoint задания, связанные попытки/статусы |

Восстанавливаются EMA, начальное SMA-накопление EMA старых версий, точные
целочисленные префиксы SMA, change/cross, кольцевые буферы истории и независимые
состояния пользовательских вызовов. Обычные переменные текущего бара вычисляются
заново на следующем баре. Запись — закрытый JSON с явными допустимыми видами
состояния; pickle и конструкторы из JSON не используются. Типы, конечные float,
int64 и внутренние широкие аккумуляторы проверяются до присваивания runtime.

Worker сверяет RunPlan, spec/profile/вычислительную реализацию, исходный вход,
хеш программы и полную идентичность dataset. При продолжении исходник не
компилируется заново: загружается закреплённый IR. Проверяются хеши всех входных
Parquet, включая пропущенный префикс, и время последнего завершённого бара.
Чтение начинается с сохранённого cursor без повторного исполнения префикса.
Низкоуровневый runtime state сам по себе не является переносимым заданием:
привязку к снимку обеспечивает манифест CheckpointStore.

Текущий CSV-хвост копируется в immutable storage; hardlink к дописываемому
файлу не используется. При восстановлении создаётся отдельная рабочая копия.
Checkpoint не закрывает неполный Parquet-блок: сохраняются границы по 100000
выходных значений. Поэтому прерывание посередине блока и даже между границами
групп `plot` даёт те же физические Parquet, что непрерывное исполнение.

## Использование

```powershell
# Новое задание: принудительная пауза после второго бара.
openpine job --source examples/pipeline/v6.pine --bars examples/pipeline/bars.json --state-dir .runtime/checkpoint-demo --pause-after 2

# Следующий процесс использует сохранённые вход, снимок и RunPlan.
openpine job --resume JOB_ID --state-dir .runtime/checkpoint-demo
```

CLI печатает `job.status=paused`, `checkpoint_id` и `response=null`; код выхода
при паузе — 0. Продолжение получает новый `attempt_id`, `resumed_from_bar` и
увеличивает `attempt_count`. Паузы не расходуют бюджет отказов. Ctrl+C сохраняет
прежнее поведение отмены. Одним state-dir владеет один координатор: для CLI
продолжения сервера с тем же каталогом его сначала останавливают.

HTTP использует прежний локальный токен/Origin:

- `POST /api/jobs/ID/pause {}` запрашивает паузу после целого бара. Для running
  ответ может ещё иметь `status=running,pause_requested=true`; подтверждение
  — последующий `GET /api/jobs/ID` со `status=paused`.
- `POST /api/jobs/ID/resume {}` возвращает paused в очередь; другие статусы
  не принимаются. Пауза queued не создаёт процесс и начинает затем с нуля.
- `POST /api/jobs` с `schema_version=openpine.job-request.3` содержит
  `input_ref`, `snapshot_id`, `timeout_seconds`, `checkpoint_interval_bars`
  и `pause_after_bars` (null либо абсолютное число баров). Прежний transport .2
  остаётся рабочим. `GET /api/jobs/ID/plan` показывает закреплённую политику.

Кнопки паузы/продолжения в UI относятся к следующему этапу интерфейса;
сейчас доступны CLI/HTTP, а paused и фазы восстановления отображаются корректно.

## Ресурсы, отказы и совместимость

По умолчанию периодический checkpoint — каждые 100000 баров.
`--checkpoint-every 0` выключает периодическое сохранение, но оставляет
принудительную/ручную паузу. Частота — часть RunPlan; продолжение её не меняет.
Каждый runtime/prefix JSON ограничен 256 MiB, история — существующим лимитом
1000000 ячеек. При превышении или отказе диска сохранение не подтверждается;
предыдущий корень остаётся целым. Частое сохранение большого состояния требует
дополнительных записи/хеширования и места под объекты до явного GC.

Автоматический повтор после падения worker/координатора использует последний
checkpoint и сохранённую политику отказов. Для него при создании задания нужен
`--max-attempts 2` или 3 (для сервера — параметр serve); default 1 сохраняет
отказ без автоматического повтора. Каждая новая попытка имеет собственный
timeout, заданный планом. Пауза и перезапуск приложения не меняют лимиты плана.

Последний checkpoint задания — корень достижимости, включая CSV-хвост. Backup,
restore и GC сохраняют его даже у paused и завершённых заданий. После явного
prune задания корень удаляется, а файлы становятся кандидатами GC согласно
grace period. Backup и restored state не содержат зависимостей от старых путей.

Каталог v2 мигрирует транзакционно в v3. Старые RunPlan .1 читаются с прежними
байтами payload и прежним хешем; периодическое сохранение для них выключено.
Изменение вычислительного ядра этого этапа меняет execution fingerprint:
прежний IR нужно перекомпилировать, а незавершённое задание старого ядра нельзя
продолжить под новым молча. Сохранённые снимки и результаты остаются читаемыми.
Новый исторический драйвер не вводит realtime, rollback тиков или мультиконтекст.

## Приёмка

`tests/test_checkpoints.py` проходит 203 исполняемых исторических сценария из
пяти корпусов для Pine v1–v6 на каждой доступной границе бара. Отдельные процессы
сверяют результат и Parquet для всех шести версий. Проверяются wrap истории,
падение worker/координатора, ручная пауза, CLI/HTTP, backup/restore/GC, ENOSPC,
чужая программа/план, повреждение состояния и запрет публикации старой попыткой.

```powershell
python -m tools.release_gate
python -m tools.install_check
python -m tools.checkpoint_benchmark --directory ../checkpoint-proof --bars 1000000 --pause-after 123457
```

Большая приёмка исполняет `var`, EMA, SMA и history, сохраняет checkpoint внутри
незаконченного блока, делает backup/restore и продолжает новым процессом.
Сравниваются вся сводка и хеши каждого Parquet-блока с непрерывным запуском;
последние значения независимо рассчитываются из синтетического входа.
Измерения и результаты общего gate: [evidence/checkpoints-20261021.json](evidence/checkpoints-20261021.json).

Локальный прогон на Python 3.14.8: миллион баров, четыре миллиона выходных
значений, 40 Parquet-блоков. После backup/restore продолжение с бара 123457
полностью совпало с непрерывным запуском. Runtime state занял 33611883 байта,
запрос задания — 226 байт, запрос worker — 1025 байт; пиковый наблюдённый RSS
worker — около 136 MiB. Непрерывное исполнение — 41,914 с, до паузы — 7,906 с,
продолжение — 37,344 с. Это измерение данного Windows-хоста, а не общий SLA.
