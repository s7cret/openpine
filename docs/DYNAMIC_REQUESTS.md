# Динамические запросы

## Основание для версионных правил

Сигнатуры ниже взяты из `entries[].parameters` закреплённого [справочника](../spec/bundles/pine-spec-20261020.1/reference). Позиции считаются от единицы, значения по умолчанию взяты из `default_claim.spellings`. Таблица описывает артефакты языка. Статус реализации ведётся в матрице покрытия.

| Pine | Декларация и режим | Инструмент и интервал |
| --- | --- | --- |
| v1 | Для `study` архивная запись, для `strategy` неподтверждённая. Основания включать динамический режим нет. | Архивная запись `security`, квалификаторы не установлены. |
| v2 | Для `study` сведения о совместимости, для `strategy` пример. Основания включать динамический режим нет. | Версионный пример `security`, квалификаторы не установлены. |
| v3 | В первичных записях `study` и `strategy` параметр отсутствует. | `security(symbol, resolution, …)`, оба аргумента имеют тип `string` без явного квалификатора. |
| v4 | В первичных записях `study` и `strategy` параметр отсутствует. | Те же два аргумента `string`. |
| v5 | `dynamic_requests` — `const bool`, по умолчанию `false`. Позиция 16 в `indicator`, 32 в `strategy`. | У `request.security` и `request.security_lower_tf` первые два параметра допускают написания `const/input/simple/series string`. |
| v6 | Те же тип и позиции, по умолчанию `true`. | У обеих функций те же квалификаторы. |

Для v5/v6 значение по умолчанию существенно при чтении программы без явного аргумента. Выбор рынка через замороженный `input` уже реализован в [профиле вычисляемых целей](COMPUTED_TARGETS.md). Набор квалификаторов в сигнатуре сам по себе не определяет момент выбора рынка, правила первого обращения на realtime или наследование контекста вложенного запроса.

## Декларация и сохранённый IR

Компилятор принимает именованный `dynamic_requests` и позиционный аргумент 16 у `indicator` или 32 у `strategy`. Явный режим записывается в идентичность программы. У прежнего IR режим определяется версией Pine. Команда `job --plan-only` показывает фактическое значение в поле `dynamic_requests`. При выключенном режиме серия строк в позиции рынка или интервала даёт `ARGUMENT_QUALIFIER`.

Для длинной позиционной записи имена предшествующих полей берутся из сигнатуры выбранной версии. У опций за пределами исполнительного профиля принимается только нейтральное значение. Например, у `indicator` допустим текущий интервал (`""` или `timeframe.period`), а явный интервал `"240"` в этой декларации даёт `DECLARATION_OPTION`. Такая запись не включает исполнение самого индикатора на другом интервале.

## Изменения в прежнем корпусе

В Pine v6 режим включён по умолчанию. В корпусах `computed-targets`, `prepared-requests`, `function-targets` и `primary-targets` прежние проверки отказа для серии теперь проходят компиляцию. Эти сценарии передают только свечи основного графика. Для исполнения требуется набор запрошенных рынков, поэтому ожидается `INPUT_INVALID/DYNAMIC_COVERAGE_MISSING`. В `numeric-targets/v6-series-target` интервал вычисляется из текущей цены. Для такого выражения статический план пока не может перечислить интервалы, и ожидается `PROFILE_UNCOVERED/REQUEST_SCOPE`. Исходники и идентификаторы этих сценариев сохранены. Парные сценарии v5 используют выключенный по умолчанию режим и сохраняют прежний `ARGUMENT_QUALIFIER`.

Закреплённый каталог может явно указать неизвестный символ. Строгий динамический вызов выдаёт `DYNAMIC_UNKNOWN_SYMBOL`, а при `ignore_invalid_symbol=true` возвращает пустое значение по типу запроса. Если снимка пары нет и каталог не подтверждает неизвестный символ, код — `DYNAMIC_COVERAGE_MISSING` при обоих значениях флага. Пропуск отдельной свечи внутри закреплённого ряда обрабатывается по `gaps`.

Когда оба аргумента запроса зависят от одной неизменяемой булевой переменной графика, план учитывает совместный выбор. Для пар A/1 и B/2 достаточно снимков A/1 и B/2. Две независимые переменные в тех же выражениях дают четыре потенциальные пары.

## Вызовы в локальных областях

Для v5 с `dynamic_requests=true` и для v6 с включённым режимом `request.security` может находиться в ветви условия, теле цикла и пользовательской функции. Планировщик подготавливает историю возможных рынков. На баре выражение Pine читает результат только при достижении вызова. В replay это относится и к вызову с буквальными символом и интервалом внутри пропущенной ветви.

Примеры используют данные и команду `job` из раздела ниже. Достаточно заменить имя исходного файла.

| Скрипт | Что проверить на шести барах |
| --- | --- |
| [Условие и функция](../examples/dynamic-requests/conditional-function.pine) | Основной график выбирает A на барах 0 и 3. При втором вызове функция возвращает предыдущее закрытие A, равное 16. Ветка B на барах 1 и 5 возвращает 37 и 48. |
| [Сканер в цикле](../examples/dynamic-requests/loop-scanner.pine) | Каждая итерация передаёт локальный символ в одну функцию. Суммы закрытий трёх рынков равны 120, 119, 141, 121, 140 и 156. Выражение цены запроса независимо от счётчика цикла. |
| [Стратегия ротации](../examples/dynamic-requests/rotation-strategy.pine) | При сигнале 90 стратегия выставляет заявку и после восстановления исполняет её на следующем открытии основного рынка по цене 1. Закрытие по 3 даёт прибыль 2, следующая покупка исполняется по 2. Конечный капитал 1002. |

[Пример для `request.security_lower_tf`](../examples/dynamic-requests/lower-rotation.pine) использует двухминутный график `primary2.json` и привязки `lower-contexts.json`. Для рынков A, B и снова A суммы минутных закрытий равны 22, 76 и 38. В каждом массиве две свечи. Восстановление после второго бара сохраняет границу следующего окна A.

## Вложенные запросы

Наследование символа и интервала в прямой цепочке из двух или трёх вызовов разобрано с числовыми примерами в [ADR-0085](adr/0085-nested-request-clock.md). Для `nested-rotation.pine` команда `job --plan-only` показывает в `context_graph.requests` три маршрута. У каждого маршрута поле `nested_requests` содержит два внутренних вызова.

## Бюджет рынков и проверка нагрузки

Пример [nested-market-clocks.pine](../examples/dynamic-requests/nested-market-clocks.pine) читает двухминутный рынок A через минутный B. На восьми барах графика цены A, наблюдаемые через B, равны `na, 10, 10, 10, 20, 30, 30, 40`. При ограничении расчёта последними двумя свечами A и тремя свечами B первые пять значений равны `na`, последние три — 30, 30 и 40.

У программы с динамическим выбором цели до 32 различных пар «символ, интервал» на весь запуск. График может иметь отдельный, 33-й снимок. Два места вызова, которые читают один рынок, используют одно место в бюджете рынков и сохраняют отдельные состояния выражений. Ограничение на 16 написанных вызовов применяется при проверке IR. Если суммарный набор целей требует 33 пары, подготовка возвращает `DYNAMIC_CONTEXT_LIMIT`.

Для изолированного worker с 32 дополнительными снимками проверена конфигурация `--workers 1 --total-memory-mb 2048 --worker-memory-mb 2048`. Планировщик учитывает общую память и минимальный бюджет для каждого читателя. Профиль 512 МиБ для этой конфигурации возвращает `RESOURCE_POLICY_INCOMPATIBLE`.

```powershell
python -m tools.dynamic_request_scale --counts 100000 1000000 --markets 1 8 32 --output .runtime/dynamic-request-scale.json
```

Измеритель выполняет статический контроль, переключение каждый бар, каждые 1024 бара и вложенный запрос с унаследованным интервалом. Основные свечи минутные, запрошенные часовые. Для обычных запросов используется закреплённый курс USD/EUR, для вложенных — исходная валюта. Проверяются хеш всех выходных значений, число открытых снимков, SQL-запросов к Parquet, запусков читателей и чтений котировок FX. RSS снимается на контрольных точках процесса.

В [результатах 20 прогонов](evidence/dynamic-request-scale-20261121.json) сохранены счётчики каждого источника и хеш полного выходного ряда. На миллионе минутных свечей с 32 часовыми рынками частая ротация заняла 161,13 с, редкая — 155,56 с, вложенный запрос на том же интервале — 158,50 с. Во всех трёх случаях каждый из 33 читателей стартовал один раз. На 42 части Parquet пришлось 42 SQL-запроса. Пиковый наблюдавшийся RSS для частой ротации составил 515 МиБ. Время измерено по одному разу на конфигурацию на Windows и зависит от нагрузки машины. Счётчик SQL отражает обращения к частям Parquet, физические обращения к диску зависят от файлового кеша ОС.

## Первое обращение в replay

Для Pine v5 с включённым режимом и Pine v6 replay запоминает маршруты, реально выбранные выражением запроса на закрытых исторических барах. Граница истории задаётся `history_last_ms` основного графика. Если на первом тике выбран ранее не использованный маршрут, выполнение завершается с `DYNAMIC_REQUEST_FIRST_REALTIME`. Даже подготовленный снимок и подтверждённая свеча этого рынка сами по себе не означают, что скрипт обращался к нему на истории. Основание для этого ограничения и пример смены интервала приведены в [руководстве TradingView](https://www.tradingview.com/pine-script-docs/concepts/other-timeframes-and-data/#dynamic-requests).

В текущем профиле маршрут закреплён за местом вызова, символом и интервалом. Контрольная точка динамического replay сохраняет исторические обращения. Для контрольных точек динамического replay, записанных до добавления этого поля, нужен повтор событий с начала. Если исторический префикс отсутствует, первое динамическое обращение на realtime завершается той же диагностикой.

В [примере переключения внутри свечи](../examples/dynamic-requests/intrabar-rotation.pine) первые шесть событий закрывают по две исторические свечи A, B и графика. После десятого события выбран B, предварительные значения цены и предыдущего закрытия равны 24 и 22. На следующем обновлении изменяется цена A, пока на графике по-прежнему выбран B. При возврате к A график показывает 17 и 12. На закрытии публикуются 18 и 12.

```powershell
$example = 'examples/dynamic-requests'
$id = (python -m apps.openpine replay create --source "$example/intrabar-rotation.pine" --contexts "$example/replay-contexts.json" | ConvertFrom-Json).replay_id
python -m apps.openpine replay append --id $id --events "$example/intrabar-events.ndjson"
python -m apps.openpine replay advance --id $id --max-events 10 --checkpoint-every 10
python -m apps.openpine replay advance --id $id
python -m apps.openpine replay chart --id $id
```

## Контрольный пример смены рынка

Стратегия [currency-strategy.pine](../examples/dynamic-requests/currency-strategy.pine) читает USD-инструмент A на барах 0, 2 и 3 и основной EUR-инструмент B на баре 1. На [четырёх свечах и двух публикациях курса](../conformance/security-currency) ожидаемый сигнал в EUR равен 50, 11, 112 и 128. На третьем баре он пересекает 100, сделка исполняется на следующей свече B по 13. После публикации исправления курса с 0,8 до 0,75 новый снимок даёт на последнем баре 120. Тест останавливает процесс после публикации контрольной точки второго бара, сохраняет новую редакцию курса и повторяет доставку части событий. Для восстановленного задания проверяются исходный ряд и полный журнал сделок.

Из корня репозитория запустите пример на Python 3.14.8. Файл `contexts.json` ссылается на три локальных набора минутных свечей. Для повторения с контрольной точкой добавьте `--pause-after 3`, затем выполните `python -m apps.openpine job --resume <job_id>` с тем же каталогом состояния.

```powershell
python -m apps.openpine job --source examples/dynamic-requests/rotation.pine --bars examples/dynamic-requests/primary.json --contexts examples/dynamic-requests/contexts.json
```

На тех же свечах [history-selector.pine](../examples/dynamic-requests/history-selector.pine) выбирает рынок A, когда средняя двух последних закрытий основного графика превышает 1 и предыдущее закрытие равно 1. Иначе выбирается B. На втором баре средняя равна 1,5, предыдущее закрытие графика равно 1, а предыдущее закрытие выбранного A равно 10. При восстановлении после первого бара эти два значения истории и окно средней нужны уже для первого расчёта. Ожидаемые цены шести баров — 30, 12, 35, 41, 18, 48. Предыдущие цены выбранного рынка — na, 10, 37, 35, 14, 36.

Три рынка имеют по одной подтверждённой свече на каждое закрытие основного графика, с одинаковыми временем, интервалом и валютой. Выражение запроса возвращает `close` и `close[1]`. На втором посещении рынка история должна относиться к предыдущей свече этого рынка. Следующая таблица рассчитана непосредственно по входным ценам.

| Бар | A | B | C | Выбор | Ожидаемый close | Ожидаемый close[1] |
| ---: | ---: | ---: | ---: | --- | ---: | ---: |
| 0 | 10 | 30 | 80 | A | 10 | na |
| 1 | 12 | 37 | 70 | B | 37 | 30 |
| 2 | 16 | 35 | 90 | C | 90 | 70 |
| 3 | 14 | 41 | 66 | A | 14 | 16 |
| 4 | 18 | 36 | 86 | C | 86 | 66 |
| 5 | 20 | 48 | 88 | B | 48 | 36 |

Для ряда A с EMA(3), инициализированной первой ценой, значения на барах 0–3 равны 10, 11, 13,5 и 13,75. Возврат к A на баре 3 различает расчёт на истории A и расчёт только по двум посещениям A, который дал бы 12. Этот пример задаёт ожидаемое поведение исторического профиля OpenPine.
