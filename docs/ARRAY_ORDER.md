# Сортировка, ранги и бинарный поиск массивов

Профиль `openpine.array-order.1` закреплён в `spec/array-order-profile.json`.
Он расширяет существующие массивы и плоские UDT через общий Binder, ArrayIR,
runtime и heap. Исходные bundles, прежние profiles и форматы heap/checkpoint
сохраняются; fingerprint реализации меняется.

| Возможность | v1–v3 | v4 | v5 | v6 |
| --- | --- | --- | --- | --- |
| `array.sort(id, order)` | отказ | int/float | int/float/string | int/float/string, плоские UDT |
| `array.sort_indices(id, order)` | отказ | отказ | int/float/string | int/float/string, плоские UDT |
| Три `array.binary_search*` | отказ | отказ | int/float | int/float, поля плоских UDT |
| `array.min/max(id, nth)` | отказ | отказ | int/float | int/float |
| Направление `order.*` | отказ | bool | sort_order | sort_order |
| Instance methods | отказ | отказ | доступны | доступны |

В v4 `order.ascending` и `order.descending` представлены bool; в ограниченном
OpenPine-профиле true означает ascending. V5/v6 используют отдельный scalar
`sort_order` с закрытыми значениями ascending/descending. Строка или bool не
превращаются в этот тип. Поддерживаются переменные, условия, равенство, история,
var/varip, UDF-параметры и defaults. Массивы, UDT-поля, tuple, inputs и новые
request expressions с sort_order исключены. Новые user-method receivers этого
типа не вводятся.

`sort` меняет существующий контейнер и виден всем aliases. `sort_indices`
создаёт отдельный array<int> с исходными позициями, сохраняя исходный порядок
элементов. По умолчанию порядок ascending. Одинаковые ключи сохраняют исходный
порядок, включая descending. Числа сравниваются без преобразования всех int в
float; строки используют Unicode-порядок. Missing и пустые строки составляют
общую стабильную группу: последнюю ascending и первую descending. Применение
этой детали к старым версиям и стабильность равных ключей — явные интерпретации
OpenPine; внешнего выполнения TradingView не проводилось.

В v6 `sort_field` выбирает поле UDT по const int-индексу или const string-имени;
по умолчанию индекс 0. Поле должно иметь тип int/float/string. Binder замыкает
выбор в literal до исполнения: доступны литералы, const-переменные и простые
чистые const-выражения; произвольные вызовы функций не сворачиваются. Input,
simple/series, неизвестное поле и bool/enum-поле дают `ARRAY_SORT_FIELD`.
Missing ID объекта при обращении к ключу даёт `UDT_NA`. Записи не копируются:
меняется порядок существующих ссылок, сохраняются shallow aliases и GC-рёбра.

Бинарный поиск требует возрастающих определённых ключей. Это предусловие
вызывающего кода: runtime не пересортировывает массив и не выполняет линейную
проверку перед каждым поиском. Работа учитывается по логарифмическим probes;
missing target или встретившийся missing key дают `ARRAY_SEARCH_NA`. Поведение
при нарушенном предусловии не является свидетельством внешней эквивалентности.

| Поиск | Найдено | Не найдено |
| --- | --- | --- |
| `binary_search` | индекс первого совпавшего среднего probe | -1 |
| `binary_search_leftmost` | первое равное значение | предшественник; минимум 0 |
| `binary_search_rightmost` | последнее равное значение | индекс следующего; может равняться size |

Для пустого массива все три возвращают -1 — явно закреплённое граничное
решение OpenPine. Результат rightmost=size нельзя сразу передать в get.
Числовые цели могут быть int или float. V6 UDT-поля допускают также string:
закреплённая типизированная перегрузка явно включает string, хотя часть prose
справочника называет только numeric. В этом профиле приоритет у сигнатуры.

`nth` — определённый неотрицательный int, начиная с нуля. Повторы считаются
отдельными слотами, na пропускается. Пустой/all-na массив даёт na; отрицательный,
missing или недоступный ранг даёт `ARRAY_RANK`. Последняя граница является
явной интерпретацией, поскольку справочник не определяет её достаточно точно.
Агрегаты не меняют порядок; старые вызовы min/max без nth и их IR сохранены.

Перед сортировкой резервируются scratch memory и финальные слоты. Линейная
подготовка, реальные сравнения и длины строк учитываются общим WorkBudget;
отмена проверяется во время работы и перед публикацией. При ошибке или отмене
исходный контейнер, COW-владение, references и ID остаются прежними, staging
освобождается. Sort_indices проверяет логические квоты до построения результата.

Лимиты прежние: 100 тысяч элементов в массиве, миллион ячеек, миллион операций
на бар и общий job memory. Уже упорядоченный массив 100 тысяч элементов
обрабатывается в этих пределах; сложный вход может исчерпать бюджет и завершиться
атомарным отказом. Durable restore проверяется для 100 тысяч ссылок на одну UDT
запись на границе и внутри бара. После restore runtime не удерживает checkpoint IO.

Корпус `conformance/array-order` содержит 138 ручных случаев: 68 исполнений и
70 отказов. В owned corpus добавлены routing v1–v6 и стратегии v5/v6. Старые
112 записей и все test ID сохраняются. Три прежних случая v4/v5/v6-uncovered-sort
сохраняют ID и источники; ожидаемый отказ явно заменён исполнением.
