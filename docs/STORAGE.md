# Хранение и исполнение R6

Python **3.14.8**, SQLite **3.54.1** через `apsw==3.54.1.0`,
DuckDB **2.0.0.dev2610192346**, Parquet с ZSTD. На 21 октября 2026 года
стабильная DuckDB 2.0.0 ещё не опубликована: используется явно закреплённая
официальная предварительная сборка, включая ABI3 wheels для Windows/Linux.
`sqlite3` из стандартной библиотеки не используется как движок каталога.

## Границы

Все компоненты находятся в этом монорепозитории. Один локальный координатор
владеет каталогом; второй владелец отклоняется файловой блокировкой.
SQLite содержит короткие транзакции управления. DuckDB использует отдельные
in-memory connections для чтения/создания Parquet, без общего изменяемого
файла `.duckdb`. Compiler/runtime не импортируют SQL-адаптеры.

`contracts/storage.py` задаёт идентичность набора, источник баров, приёмник
выходов и бюджет процессов. `marketdata` отвечает за правила свечей/провайдеров,
`execution` — за порядок исполнения и попытки, `storage` — за форматы и I/O.

## Файлы и идентичности

```text
.runtime/jobs/
  catalog.sqlite3              # SQLite, user_version и миграции
  catalog.sqlite3-wal          # служебные файлы WAL при открытой базе
  catalog.sqlite3-shm
  objects/<первые 2 символа>/<sha256>
  attempts/<job_id>/<attempt_id>/
    request.json               # ссылки и бюджет, без свечей/IR
    heartbeat.json             # время, попытка, фаза, прогресс
    completion.json            # attempt_id и result_id
    worker.log
```

Объекты: исходник или IR, JSON-манифест снимка, блоки свечей Parquet,
JSON-сводка результата и блоки выходных рядов Parquet. SHA-256 файла проверяется
перед чтением. Повторная запись одинакового объекта не создаёт вторую копию.
Публикация: временный файл → flush/fsync → атомарная неизменяемая ссылка →
транзакция каталога. При сбое до транзакции может остаться объект без ссылки;
он не считается опубликованным результатом. Автоматического удаления объектов нет.

Запрос `openpine.job-request.2` содержит `input_ref`, `snapshot_id`,
`timeout_seconds`. Задание имеет стабильный случайный `job_id`; каждая попытка
имеет новый `attempt_id`. Успех и ссылка на результат фиксируются одной
транзакцией с завершением попытки. Поздний результат старой попытки не принимается.

Скомпилированный вход хранит `artifact_ref` и, когда исходник передан приложению,
`source_ref`. IR не вкладывается повторно в запрос или сводку результата;
исходный текст также сохраняется отдельным общим объектом.

Программа сохраняет текущие проверки спецификации, Pine v1–v6, профиля и
реализации. Хеш реализации включает исходники, Python и версии зависимостей.

## Свечи

`openpine.dataset-snapshot.2`: метаданные ряда, логическая идентичность,
неизменяемый список блоков и точные границы выборки, provenance. Ряд задаётся
пространством источника/рынка, символом и таймфреймом. Например,
`binance.spot.rest.1` отделяет Binance Spot от других рынков/версий источника.

OHLCV: UTC milliseconds `BIGINT` для открытия, nullable `DOUBLE` для цен и
объёма. Валидация сохраняет пропуски, `na` и signed zero. Порядок строго
хронологический, без повторного времени открытия. Один блок — до 100000 баров;
один импорт — до 10000000. Чтение идёт порциями до 8192 строк.

Логический хеш `openpine.candle-rows.1` считается по каноническим метаданным и
бинарным полям строк (big-endian int64, наличие значения, binary64). Он не
зависит от сжатия и границ блоков. Хеши физических Parquet и манифеста отдельны.
Для импортированного `market-snapshot.1` сохраняются старые snapshot/data IDs;
дополнительно проверяется новый логический хеш, точный обратный JSON-экспорт
проходит прежнюю проверку идентичности.

Каталог покрытия хранит интервалы `[start,end)`, а не только min/max свечей.
`ensure()` запрашивает недостающие интервалы, ограничивая REST-запросы суточными
окнами. Полностью полученный пустой интервал тоже отмечается. Частичный ответ
при сетевой ошибке покрытием не считается. Пропуски внутри успешного ответа
сохраняются. `refresh` создаёт новую ревизию; новый ответ владеет всем своим
интервалом, включая удалённые поставщиком свечи. Старый снимок остаётся доступен.

Граница подтверждённого покрытия учитывает фактическое время закрытия Binance.
Наблюдавшаяся незакрытая свеча остаётся за пределами покрытия: после её закрытия
следующий запрос догружает её, включая месячные бары без вычисления их длины.

## Попытки и ресурсы

По умолчанию: 2 процесса, по 1 потоку DuckDB, по 512 MiB RSS, суммарно 1024 MiB,
очередь 32 задания. DuckDB получает отдельный лимит памяти до 128 MB и временных
файлов до 512 MB. RSS проверяется примерно каждые 100 ms: превышение завершает
процесс, поэтому это мониторинг с возможным кратковременным превышением,
а не ограничение адресного пространства ОС.

Heartbeat записывается каждые 0.5 s, срок ожидания по умолчанию 15 s. Прогресс
расчёта обновляется через 1000 баров. Состояние runtime, список времён и все
выходные массивы не накапливаются для большого запуска: выходы уходят в sink.
Существующие ограниченные буферы истории Pine сохраняют прежнюю семантику.

`--max-attempts 1` — без автоматических повторов. Значение 2 или 3 разрешает
повторы инфраструктурных сбоев: запуск/падение процесса, heartbeat, перезапуск
координатора. Ошибка Pine, отмена, лимит памяти и таймаут не повторяются.
Таймаут (до 3600 s) относится к каждой попытке и включает запуск, компиляцию,
чтение и публикацию. Очередь после аварии сохраняется; прерванные попытки
обрабатываются указанной политикой. Штатное закрытие отменяет активные задания.

```sh
python -m apps.openpine serve --workers 2 --threads-per-worker 1 --worker-memory-mb 512 --total-memory-mb 1024 --max-attempts 2
```

## Результаты и веб

Сводка `openpine.run-summary.3` содержит число наблюдений, идентичности,
описания рядов, count/null_count/last и ссылки на блоки. В Parquet выходов
хранятся bar_index, time, output_id и точный JSON-скаляр значения: это сохраняет
64-bit int, float, `null` и signed zero без приведения всех результатов к DOUBLE.

HTTP:

- `GET /api/datasets/<snapshot_id>` — манифест без массива свечей.
- `GET /api/jobs/<job_id>/request` — компактный запрос по ссылкам.
- `GET /api/jobs/<job_id>/summary` — сводка без массивов выходов.
- `GET /api/jobs/<job_id>/chart?start=0&limit=2000` — окно, максимум 5000 баров.
- `GET /api/datasets/<snapshot_id>/parts/<object_id>` — блок свечей Parquet.
- `GET /api/jobs/<job_id>/series/<object_id>` — блок выходов Parquet.
- `GET /api/jobs/<job_id>/result` — полный прежний JSON для запусков до 100000
  баров; выше — сводка и ссылки на блоки.

Веб загружает метаданные и окна по 2000 баров. Кнопки предыдущего/следующего
окна меняют диапазон; масштаб и сдвиг действуют внутри загруженного окна.
Для больших экспортов нужны JSON-манифест и перечисленные Parquet-блоки.
Файловые ссылки доступны только через принадлежащий запуску/снимку манифест.

## Миграция и эксплуатация

При первом открытии каталогов старые `<job_id>/status.json`, `request.json`,
`result.json` импортируются один раз. Исходные файлы сохраняются побайтово.
Невалидные записи отмечаются в `imports`, видны через `storage inspect`.
Старые снимки веб-приложения также импортируются при первом открытии сервера.
Следующие старты используют индекс SQLite и не сканируют всю историю JSON.

```sh
python -m apps.openpine storage import --bars examples/pipeline/bars.json
python -m apps.openpine storage import --csv candles.csv --context-id binance.spot.BTCUSDT.1 --symbol BINANCE:BTCUSDT --timeframe 1
python -m apps.openpine storage fetch --symbol BINANCE:BTCUSDT --timeframe 1 --start-ms 1792454400000 --end-ms 1792540800000
python -m apps.openpine job --source examples/pipeline/v6.pine --snapshot-id <snapshot_id> --timeout 3600
python -m apps.openpine storage inspect
python -m apps.openpine storage backup --destination ../openpine-backup
python -m apps.openpine storage restore --source ../openpine-backup --state-dir ../restored-jobs
```

CSV содержит заголовки `time,open,high,low,close,volume`; пустое поле означает
`na`. JSON-импорт/прежний CLI остаются ограниченными небольшими входами.
Команды администрирования берут ту же блокировку владельца: для них сервер
нужно остановить. Функция backup внутри координатора допускает работающие
воркеры: SQLite backup API фиксирует согласованный каталог, а все ранее
опубликованные объекты неизменяемы и не удаляются.

Резервная копия содержит SQLite и объекты с контрольными суммами. Восстановление
проверяет контрольные суммы и SQLite integrity/foreign keys и публикует новый
каталог только после проверок. Существующий каталог назначения не заменяется.

## Приёмка

Обычный gate включает миграцию, реальное исполнение всех Pine v1–v6,
конкурентные процессы, отмену/таймаут/падение координатора, повторную попытку,
поздний результат, повреждение объектов, SQL FULL/ENOSPC, покрытие/ревизии,
порционную выдачу и восстановление backup.

Большой прогон запускается явно, отдельно от каждого обычного CI:

```sh
python -m tools.storage_benchmark --directory ../storage-proof
```

Он создаёт 100000, 1000000 и 10000000 синтетических свечей без полного массива
в памяти, исполняет `plot(close)` в настоящих процессах, проверяет число/последнее
значение выходов, последнее окно графика, общие ссылки, конкуренцию, память,
а также backup/restore большого набора. `report.json` содержит фактические
версии, времена, размер запросов, идентификаторы и пиковый sampled RSS.

Нехватка места воспроизводится реальным лимитом SQLite `max_page_count` и
управляемой инъекцией ENOSPC в публикацию файла; отдельно проверяется отказ
записи метаданных и остановка scheduler без публикации ложного успеха.
