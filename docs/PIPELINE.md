# Исторический путь OpenPine

Требуется Python **3.14.8**. [План и приёмка](PIPELINE_PLAN.md),
[SQLite 3.54.1, DuckDB 2.0 и Parquet](STORAGE.md).

## CLI и переносимая компиляция

```sh
python -m pip install -r requirements-dev.txt
python -m apps.openpine run --source examples/pipeline/v6.pine --bars examples/pipeline/bars.json
python -m apps.openpine compile --source examples/pipeline/v6.pine --profile historical --output compiled.json
python -m apps.openpine run --artifact compiled.json --bars examples/pipeline/bars.json --output result.json
```

В `result.outputs` находятся три ряда: `[10,40,85,135]`, `[1,3,4,5]` и
`[0,10,20,30]`. Программы v1–v5 дают те же значения на этих входах. Наблюдения
не вычисляются заново для формирования ожидаемых таблиц.

`compile` сохраняет прежние поля ответа и добавляет `artifact`. Самостоятельный
артефакт — этот объект с версией `openpine.program-artifact.1`. Загрузка принимает
его или полный ответ CLI `compile`. Артефакт содержит типизированные закрытые
JSON-записи с явными тегами, хеш программы и identity. Он не содержит
исполняемого Python. Исходный Pine при загрузке артефакта не компилируется.

Проверяются поля и типы записей, хеш содержимого, версии Pine/IR, spec lock,
семантический профиль и хеш реализации; затем runtime проверяет весь граф IR до
первого эффекта. Хеш обеспечивает целостность, а не удостоверяет автора.
Артефакты привязаны к установленной реализации; после её изменения их следует
скомпилировать заново. Повторное исполнение создаёт новое состояние.

`Application` в `packages.execution.service` обслуживает CLI, а далее worker и
HTTP. `CompileRequest` / `RunRequest` и статусы задания определены в contracts.
Диагностика сохраняет категорию, код, Pine-версию и позицию в исходнике.

## Исторические данные

`HistoricalProvider.fetch(DataQuery)` возвращает `MarketSnapshot`. `FileProvider`
читает существующие `.1` close-only и `.2` OHLCV-файлы. Запрос явно задаёт symbol,
timeframe и диапазон **[start_ms,end_ms)** по времени открытия в UTC. Другой
symbol/timeframe, пустой диапазон или отсутствие баров дают диагностированный
отказ. Пропуски сохраняются, бары не достраиваются и не ресемплируются. Окна
индикаторов начинают прогрев с первого выбранного бара; дополнительные бары
для прогрева необходимо включить в запрошенный диапазон самостоятельно.

JSON-снимок содержит нормализованные данные, хеш данных, provenance запроса и
хеш всего снимка. Отдельный `fetch` сохраняет его через `SnapshotStore`.
Управляемые задания и веб используют каталог SQLite и неизменяемые Parquet-блоки,
сохраняя прежние идентичности импортированных JSON. Вычисления
получают неизменяемые данные и не обращаются к провайдеру внутри бара.

## Отдельный worker

```sh
python -m apps.openpine job --source examples/pipeline/v6.pine --bars examples/pipeline/bars.json --output job-result.json
python -m apps.openpine job --artifact compiled.json --bars examples/pipeline/bars.json --timeout 30
```

Команда ждёт завершения задания; Ctrl+C отменяет его. `--state-dir` по умолчанию
`.runtime/jobs`. Эта папка принадлежит одному приложению одновременно (ОС-lock).
Статусы, ссылки запроса и попытки сохраняются транзакциями SQLite; свечи и IR
сохраняются один раз в общем хранилище. Результат
проверяется по хешу при чтении. Статусы: queued, running, succeeded, failed,
cancelled, timed_out. Ошибка компиляции — failed с исходной диагностикой.

Один subprocess обслуживает одно задание; по умолчанию до двух одновременно,
очередь до 32 незавершённых заданий. Время запуска/компиляции входит в timeout
(0 < timeout <= 3600 секунд на попытку). Supervisor принудительно завершает процесс при
отмене/таймауте. Частичные результаты не выдаются. Прогресс обновляется раз в
1000 баров и на последнем баре, heartbeat — каждые 0.5 секунды. Новый процесс
всегда начинает с пустым состоянием. Worker следит за смертью хозяина; после
перезапуска очередь сохраняется, прерванная попытка повторяется согласно
`--max-attempts` либо становится failed/HOST_RESTARTED. Завершённые результаты
остаются доступны. Большие выходы пишутся блоками Parquet, в каталоге хранится
небольшая сводка. До 100000 баров доступен прежний полный JSON; для больших
экспортов используются манифест и блоки. subprocess изолирует состояние и
сбои, но не предоставляет ОС-песочницу. Проверки: `tests/test_jobs.py`.

## Реальные котировки и офлайн-повтор

```sh
python -m apps.openpine fetch --provider binance --symbol BINANCE:BTCUSDT --timeframe 60 --start-ms 1704067200000 --end-ms 1704153600000 --output btc.json
python -m apps.openpine job --source examples/pipeline/v6.pine --bars btc.json --output btc-result.json
```

Первый вызов получает 24 часовых бара 2024-01-01, сохраняет content-addressed
снимок в `.runtime/snapshots` и экспортирует его в `btc.json`. Второй и следующие
запуски используют файл офлайн. Веб и CLI используют один `BinanceProvider`.

Поддерживается публичный **Binance Spot** через `data-api.binance.vision`, без
ключей. Канонические интервалы: 1/3/5/15/30/60/120/240/360/480/720, D/W/M.
Параметры и 12 полей kline сверены с [официальным API](https://developers.binance.com/en/docs/catalog/core-trading-spot-trading/api/rest-api/market).
[Публичный endpoint](https://developers.binance.com/en/docs/products/spot/rest-api)
предназначен для рыночных данных. Проверено 2026-10-21.

Источник старого подхода: `origin/main` на `af697b2`, файлы
`openpine/data/direct_data_provider.py` и `direct_provider.py`. Сохранены идеи
отдельного адаптера, явного запроса и пагинации. Реализация R6 использует общие
контракты монорепозитория. Курсор продвигается по фактическому open time + 1 ms;
подтверждённость определяется **close time из ответа < server time**, включая
месячные бары. Ошибки сети/данных не превращаются в частичный успех. Дубликаты,
нарушение порядка, неверные OHLCV и неподдержанные запросы отклоняются.

Диапазон задаётся временем открытия; end должен быть не позже server time.
Пропуски/начало листинга сохраняются без дополнения; фактические времена доступны
в снимке. Provenance хранит запрос, время сервера, endpoint и хеш каждой страницы.
Лимиты: 100000 баров, 101 страница, 60 секунд между началом пагинации и стартом
следующей страницы; отдельный HTTP-запрос имеет timeout 10 секунд. При HTTP
ошибке отдельный запрос завершается явно. `storage fetch` и веб сохраняют
только успешно полученные интервалы покрытия и догружают недостающие;
незакрытая свеча не помечается как готовая история. Подробности в [STORAGE.md](STORAGE.md).
Офлайн gate использует собственные подставные страницы (`test_binance.py`),
доступность биржи проверяется отдельно командой выше.

## Веб-интерфейс

```sh
python -m apps.openpine serve
```

Откройте напечатанный `http://127.0.0.1:PORT`. Свободный порт выбирает ОС;
`--port 8765` задаёт фиксированный порт, если он свободен. `--state-dir` по
умолчанию `.runtime`, каталог и объекты сохраняются внутри `jobs`. Сервер работает только
на loopback. Остановка — Ctrl+C; активные задания отменяются.

1. Загрузите `.pine` или откройте пример v1–v6. Редактор допускает исправления.
2. Выберите demo, OHLCV/снимок из JSON либо Binance Spot и исторический UTC
   диапазон. Нажмите «Подготовить данные». В снимке показаны реальные границы и
   число баров. Изменение параметров требует подготовки нового снимка.
3. «Компилировать» проверяет исходник и позволяет скачать IR. «Запустить»
   компилирует текущий текст при необходимости и передаёт артефакт worker.
   «Остановить» отменяет задание. Прогресс и терминальный статус видны отдельно.
4. График цены отделён от выходных рядов. Данные загружаются окнами по 2000
   баров; кнопки переключают окна. Колесо изменяет масштаб, перетаскивание
   сдвигает диапазон внутри окна, легенда скрывает отдельные ряды. Для больших программ
   отображаются первые 32 ряда; экспорт содержит все выходы. Таблица показывает
   последние значения и число na. Диагностика ведёт к исходной позиции.
5. Скачайте результат/снимок и повторите запуск офлайн через CLI. История
   завершённых заданий доступна после перезапуска приложения.

Встроенный HTTP-адаптер и интерфейс не требуют Node.js или внешнего CDN.
Для запросов используется JSON и случайный токен текущего процесса. Основные
маршруты: GET `/api/config`, `/api/examples/N`, `/api/snapshots/HASH`,
`/api/jobs`, `/api/jobs/ID[/result|/request]`; POST `/api/compile`,
`/api/snapshots`, `/api/jobs`, `/api/jobs/ID/cancel`.
POST требует `Content-Type: application/json`, `X-OpenPine-Token` из config и
собственный Origin, когда браузер его передаёт. Удалённый хостинг не входит в
этот локальный профиль.

Формат артефакта сохраняет float как `{"$float":"hex"}`, а целые за пределами
безопасного диапазона JavaScript — как `{"$int":"decimal"}`. Это сохраняет
тип, signed zero и хеш при передаче через браузер. JSON-файлы данных загружаются
на сервер исходным текстом; результат и снимок скачиваются исходными байтами
с сервера. Визуальное представление графика округляет числа, файлы сохраняют
точные значения реализации.

Проверки: `python -m unittest discover -s tests -p "test_*application*.py" -v`,
`test_pipeline.py`, `test_providers.py`, `test_artifacts.py`; общий gate:
`python -m tools.release_gate`.


## Чистая установка и проверка дистрибутива

Проверьте `python --version`: для разработки/приёмки требуется **3.14.8**.
Создайте отдельное окружение, затем установите продукт:

```powershell
python -m venv .venv
.venv\Scripts\python.exe -m pip install .
.venv\Scripts\openpine.exe serve
```

На Linux соответствующие команды: `.venv/bin/python -m pip install .`,
`.venv/bin/openpine serve`. Зависимости закреплены в `pyproject.toml`; внешних
модулей OpenPine нет. Node.js, биржевые ключи и отдельные репозитории не нужны.
Первоначальная установка зависимостей использует индекс пакетов, дальнейшая
работа со снимками офлайн.

Готовый wheel можно собрать без дополнительных build-зависимостей:

```sh
python -m tools.build_backend
python -m pip install dist/openpine-5.0.0rc6-py3-none-any.whl
```

Стандартный PEP 517 backend сохраняет один общий корень пакетов, замороженных
spec-артефактов, attribution, примеров, корпуса и проверок. Установленный продукт
проверяет те же байты и хеши. Собственный код под MIT; сторонние материалы
сохраняют attribution/лицензии внутри spec и не перелицензируются.

Общий gate: `python -m tools.release_gate` (все unit/integration и conformance).
`python -m tools.install_check` отдельно собирает wheel, устанавливает его через pip в
пустой target без сети/новых зависимостей и запускает приёмку из пустого рабочего
каталога с удалением исходного checkout из пути импорта. Этот шаг выполняется
в CI на обеих ОС. Для embedded Python без pip можно передать официальный
`--pip-runner /path/to/pip.pyz`.

Приёмка установленного приложения (`tools.installed_smoke`) проверяет CLI
compile → сохранение → загрузку → run для всех v1–v6, отдельный worker, HTTP,
SQLite/Parquet, порционный график, CLI backup/restore и повтор по snapshot ID,
идентичность вычислительного результата CLI/HTTP для v1/v6. Тесты также проверяют
ошибочный исходник/данные/IR, отмену, timeout, падение worker/хозяина, повторные
запуски, независимость состояния, целостность файлов и конфликт владельцев.
Живой Binance и настоящий браузер проверяются отдельно от офлайн gate.

При сквозной проверке выявлены и исправлены четыре разрыва: потеря типа/точности
чисел JSON в браузере, Windows sharing violation при чтении/замене progress и
непопадание extensionless LICENSE из bundle в wheel и прямое скачивание JSON во встроенном браузере. На каждый добавлена
проверка воспроизведения. Для веб проверены узкая и широкая компоновки,
загрузка Pine v1, исполнение v1/v6 и отображение диагностики.


В первой приёмке сквозного пути, до перехода на SQLite/Parquet, на отдельной
установленной Python 3.14.8 выполнен полный браузерный
путь: загрузка Pine-файла → получение реальных Binance OHLCV → worker → график →
скачивание IR, снимка и результата. Эти три скачанных файла повторно загружены
в установленный сервис с заблокированным `socket.connect`: весь RunResult,
program hash и snapshot hash совпали. Проверены загрузка JSON-снимка и отмена
задания через кнопку. Метаданные локального доказательства: 24 бара,
`data_sha256=71c054f6147293319cb7a2137a9044976a4b70c01d363431b0495318d1ca58e0`.
