# Этап 2 — явный получатель пользовательского метода

Локальное продолжение numeric/index поставки `8cb17ba3395e610c73cf3feca88ca9c109fb4cb6`.
Предыдущие численные корпуса и root-исправление PineLib сохранены. Remote refs,
Actions и release-ветки этим блоком не меняются.

## Реализованный общий механизм

Поддержаны `object.method(...)`, локальный `method(object, ...)` и вызов
`library.method(object, ...)` для уже допущенного same-version профиля Pine 5/6.
Выбор выполняет существующий MethodCandidates/SignatureResolver: тип, квалификатор
получателя, overload, именованные параметры и defaults принадлежат точной декларации.
Нет обёрток, строковой замены тела метода или второго evaluator.

Первое воспроизведённое расхождение: parser допускал function-style вызов, но его
consumer bundle не содержал обязательной аргументной type evidence. Другой старый
validator видел параметры без receiver и ошибочно отклонял допустимое число
аргументов. Оба пути теперь используют общий method resolver, не таблицу по имени.

Linker разрешает явный namespace только в указанном исходном модуле и только для
экспортируемого метода. Private helpers остаются внутри библиотеки, транзитивная
зависимость не становится прямым импортом потребителя. Два одинаково названных
метода разных библиотек можно вызвать явно через разные aliases без смешивания
номинальных типов. При неоднозначном dot-вызове прежняя ошибка сохраняется.

Идентичность проекции включает полный callee range: наружный chained call и
внутренний namespace-call могут начинаться с одного символа. Привязка только по
start-offset недостаточна. Меняется только токен выбранного callee; аргументы,
комментарии, строки, тела и written callsite сохраняются.

## Compiler и состояние

Новая capability `user_method_function_calls_v1` — контракт компилятора, не runtime
операция. Producer вычисляет её из bounded AST и при source-free admission заново
восстанавливает semantic facts существующим декодером/анализатором. Пересчитанные
хеши не дают подменить receiver, qualifier, default или const facts. Старые
потребители не должны молча исполнять новый bundle без этого контракта.

Генератор использует существующий invoke_function_v1, локальные серии, heap и
checkpoint. Получатель UDT сравнивается через канонический runtime type owner, а
не как текстовое имя, созданное linker.

Исправлен порядок вычисления явно заданных аргументов пользовательских вызовов:
словарь runtime-аргументов формируется в порядке исходной записи. Именованный
receiver может стоять последним. Это не переставляет декларации и не вызывает
аргумент повторно. Пример с Counter.take(): первый аргумент получает 1, receiver
получает 2, результат receiver*10+other = 21; следующие бары дают 43 и 65.
В dot-форме неявный receiver остаётся первым. Обычные функции используют тот же
механизм сборки аргументов. Всеобъемлющая семантика side-effectful defaults не
объявляется принятой этим ограниченным корпусом.

## Покрытые сценарии

Проверены int/float, array/map/matrix, UDT/enum, именованный receiver, перегрузки,
составные callee, private/transitive calls, точная namespace identity, result
qualifier floor, отсутствие переноса methods в v1–v4 и сохранность старых bundles.

Два записанных счётчика имеют последовательности 1/2/3 и 10/20/30. В цикле один
callsite выполняется трижды и даёт 3/6/9. JSON restore совпадает с непрерывным
исполнением. Обычные поля UDT откатываются между realtime-тиками, varip-поля
сохраняют изменения; проверены четыре варианта version × imported.

Брокерный сценарий: два Counter получают 3 и 30 на третьем баре; shallow copy
первого получает 103, оригинал остаётся 3. Стратегия отправляет реальный entry
qty=3 по цене 102 на закрытии либо 103 на следующем открытии. Проверяются
bulk/interactive, Pine 5/6, local/imported и fill-recalculation. IPC в этих тестах
подставлен in-process; четыре отдельные проверки требуют настоящего sandbox.

Ожидания выведены вручную из тел методов. Внешние TradingView execution exports
не использовались; `tradingview_verified=false`.

## Приёмка и остаток

Новые test IDs: 57 producer, 57 compiler, 26 host — всего 140. Старые 21 306 ID
сохранены; обязательный состав 21 446. Producer/compiler полностью collected;
host inventory — прежний locked full set плюс реально collected новый модуль.
Это не заявление о прохождении всех 21 446 случаев. Результаты исполнения и
ограничения окружения записываются в отдельном локальном receipt после прогонов.

IMPORT-01 отмечен implemented_local_pending_joint, не accepted. Исходные 16 пакетов
и четыре критерия не удалены. IMPORT-02 (межверсионные зависимости) и остальная
полнота импортов остаются открытыми. Новый путь ограничен существующим профилем
method declarations: defaults receiver и все смешанные function/method overloads
одного имени этим блоком не принимаются; обычный function lookup сохраняет прежний
приоритет. Иные namespace-объекты не угадываются как импорт библиотек.

Предыдущий strict numeric index был красным из-за UNVERIFIED ожидаемых строк v5
str.tonumber. Этот блок не меняет эти значения или runtime семантику и не присваивает
новым source pins успешность прежнего численного прогона. Полный Stage 2 остаётся
in_progress. Новый joint CI, Python 3.11 и frontend требуют отдельной приёмки.
